# Web 服务端拆分与迁移实施计划

## 1. 目标

在不改变现有 `/api` 接口、权限规则、数据目录、启动命令和部署方式的前提下，把当前 `web_server.py` 从“所有职责集中在一个文件”迁移为可按领域阅读和测试的后端模块。

本次拆分的目标不是机械降低文件行数，而是建立稳定的维护边界：

- 启动入口只负责组装服务，不承载业务细节；
- HTTP 协议处理与业务服务分离；
- 数据库连接、建表和迁移分离；
- 每个业务领域拥有独立的服务模块；
- 所有接口返回结构、错误文本和权限结果保持兼容；
- 新增功能能够在单个领域模块内完成，减少跨文件修改。

## 2. 当前问题基线

截至本计划制定时，`web_server.py` 约 6900 行，其中：

- `Handler` 约 4400 行，包含 160 多个 HTTP 与业务方法；
- `init_db()` 约 570 行，同时包含建表、增量字段迁移和历史数据整理；
- 文件同时承担认证、任务、文件库、现场问题、日清看板、主数据、备份、消息和静态资源服务；
- 数据库 SQL、权限校验、文件路径校验、业务聚合和 HTTP 响应相互交织。

这些静态指标本身不是缺陷，但说明维护边界已经模糊，适合进行渐进式模块化。

## 4. 分阶段实施

### 阶段一：建立基础设施边界

1. 新建 `web_backend` 包及中文模块说明。
2. 抽出 `ApiError`、运行参数和 SQLite 连接对象。
3. 抽出 JSON 读取、路径安全和公共 HTTP 协议工具。
4. `web_server.py` 继续保留同名函数兼容旧测试和内部调用。

验收：服务可以正常启动，健康检查、登录和已有测试不变。

### 阶段二：迁移路由分发

1. 抽出精确路由、动态路由和文件上传优先级规则。
2. `Handler` 只保留请求读取、异常转换和业务方法调用。
3. 保留历史版本文件下载、图片下载等容易发生冲突的动态路由回归测试。

验收：四种 HTTP 方法路由结果与原版本一致，所有 Web API 回归通过。

### 阶段三：迁移数据库初始化

1. 将 `init_db()` 拆为基础表创建、字段补齐、索引创建、历史数据整理和管理员初始化。
2. 每次迁移使用明确版本标记或幂等检查，禁止通过异常静默跳过迁移。
3. 启动入口只调用 `database.initialize()`。

验收：新空目录和已有生产数据库均可启动；数据库备份、恢复和升级测试通过。

### 阶段四：按业务域迁移 Handler 方法

迁移顺序固定为：

1. 认证与账号；
2. 任务与人工复核；
3. 文件数据库与共享文件；
4. 现场问题；
5. 日清看板；
6. 主数据；
7. 管理、备份和回收站；
8. 消息通知和报表下载。

每个领域采用“服务函数接收请求上下文，返回业务结果；Handler 只负责协议响应”的模式。

验收：每迁移一个领域，运行对应测试和 Web API 测试；不允许通过复制两份实现长期过渡。

### 阶段五：收缩兼容入口

1. `web_server.py` 只保留配置加载、服务创建、维护线程和 `main()`。
2. 对外仍保留 `python web_server.py`、PyInstaller 入口和现有 GUI 启动方式。
3. 删除迁移期间产生的重复包装函数和旧路由实现。

验收：Windows 服务端、Linux 部署包、桌面端连接和 Cloudflare/Caddy 反向代理均可继续使用。

## 5. 迁移约束

- 不更换标准库 HTTP 服务框架，不在本轮引入 FastAPI 等新运行时。
- 不改变 API 路径、HTTP 方法、状态码、返回 JSON 字段和中文错误文本。
- 不改变 `web-data` 目录结构和账号数据隔离规则。
- 不把业务 SQL 复制到多个模块；数据库访问必须通过连接/事务边界完成。
- 不使用通用 `except Exception: pass` 掩盖迁移错误。
- 每个新模块必须有中文模块说明和公共函数 docstring。
- 修改后同步更新项目全景文档和测试。

## 6. 测试与发布验收

```powershell
$env:PYTHONIOENCODING="utf-8"
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_*.py"
npm --prefix web-app run build
npm --prefix tauri-app run build
cd tauri-app\src-tauri
cargo test
```

最终重新生成纯净源码包，并确认压缩包不包含 `.venv`、`node_modules`、`web-data`、`target`、构建产物、日志、可执行文件和真实业务数据。

## 7. 回滚策略

每个阶段只提交可独立运行的代码。若某一领域迁移失败：

1. 保留已经通过测试的基础模块；
2. 让兼容入口暂时继续调用原实现；
3. 不回滚数据库中的已完成幂等迁移；
4. 修复后再重新切换该领域的路由绑定。

## 8. 当前迁移进度

截至 2026 年 8 月 10 日，`web_server.py` 已从约 6900 行收缩至约 1840 行，`Handler` 从约 4400 行收缩至约 560 行。当前 131 个 Handler 方法主要是路由要求的薄委托和少量兼容入口。已完成：

- 运行配置、错误类型、JSON 兼容读取和 SQLite 连接边界；
- HTTP 路由表与统一路由分发；
- 数据库建表、字段补齐和历史数据迁移；
- 认证、管理员账号、消息与公告；
- 任务、人工复核、版本、预览、指派与分享；
- 文件数据库、现场问题和日清管理；
- 输出保留、草稿清理与周期维护；
- 管理员数据总览、审计记录、备份和回收站。
- 正式主数据档案、表格学习、重复检测、冲突治理、确认、拒绝、合并与导出。
- 报表中心生成与受控下载、批次跟踪、周报和月报周期任务。
- 工作台轻量概览、个人任务趋势、最近任务、结果文件和通知聚合。
- 普通业务文件上传、上传批次解析、跨账号引用拒绝和上传目录边界校验。
- JSON 请求读取、统一错误转换、Cookie/请求头会话解析和角色权限上下文。
- 通用流式文件响应，以及入口页、哈希资源和固定名称资源的三档缓存策略。
- 文件库的上传长度、配额、编号、权限记录查询和公共查询片段已归入 `services/library.py`，不再依赖 Handler 私有实现。
- 现场问题的编号、图片编号、可见性查询、图片读取和模板字段规范化已归入 `services/workshop.py`；五类标准问题模板、发布条件和乐观锁行为保持不变。
- 日清人员、生产班组与班次、考勤、事项、生产计划、资料上传的编号解析、字段校验、查询和路径边界已归入 `services/daily_management.py`。日清快照通过公开的只读查询函数组合现场问题和考勤数据，不再反向调用 Handler 私有方法。
- 通用单段路径编号和管理员账号动作编号由 `http/path_params.py` 统一解析；认证、账号、公告、任务模板、管理员数据和日清服务不再借用 Handler 的路径私有方法。
- HTTP 服务创建、维护调度、启动提示和关闭流程已迁入 `server_runtime.py`。`web_server.py` 只组装运行时依赖并保留 `main()` 兼容入口，`python web_server.py`、GUI 和部署包启动方式不变。
- 账号、日清考勤、生产班组、事项、生产计划、日清资料、消息公告、文件库和现场问题的公开字段整理已迁入 `presenters.py`；入口保留同名兼容别名，API 字段和权限计算不变。
- 源码包、Linux 完整包、Linux 增量补丁和 Windows PyInstaller 均显式收集 `web_backend`。Linux 安装与升级流程会校验、暂存、备份、回滚、设置权限并编译检查拆分模块，旧安装中尚无 `web_backend` 时也可通过增量补丁升级。

当前回收站使用分类恢复器注册表，新增可恢复数据类型时只需增加对应恢复函数和注册项，不再扩展长条件分支。任务恢复同时保留指派人；可选关联账号已删除时安全回落为未指派。

批次跟踪现在从当前账号最近 300 个任务中统一检查标题、动作和结果文件名，避免批次号只出现在输出文件名时被预过滤漏掉。报表下载仍限制在 `web-data/reports` 内，周期报表状态采用临时文件原子替换并保持原公开函数兼容。

临时业务上传在文件流与数据库记录之间增加失败清理，写入记录失败或上传中断时不会遗留孤立文件。`resolve_uploads()` 和 `_owned_upload_path()` 继续保留兼容入口，但唯一实现已迁入上传服务。

各领域下载接口统一调用 `Handler.send_file()`，由 `web_backend.http.responses` 负责内容类型、长度、UTF-8 文件名、缓存头和分块传输。现场图片仍使用内联响应和短时私有缓存，业务文件与报表仍禁止缓存，接口行为保持不变。

会话识别和权限判断已迁入 `web_backend.http.context`。静态资源由 `static_files.py` 托管：`index.html` 与前端路由回退不缓存，Vite 哈希资源永久缓存，其余固定名称资源缓存七天。

后续迁移顺序：

1. 迁移任务桥接执行、任务结果收集和任务公开结构；
2. 继续收缩已完成领域的兼容包装与依赖工厂；
3. 执行全量测试、双前端构建和部署入口验收。
