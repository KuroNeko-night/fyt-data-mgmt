## 先判断你要从哪里开始

2. 域名、服务器公网 IP、服务器登录方式。
3. Linux 部署包和对应的 `.sha256` 校验文件。
4. 一个准备使用的完整访问域名，例如 `fyt.example.com`。

## 0.1 先认识这些词

> **可能遇到：**分不清域名、IP、DNS、端口、安全组、Caddy、证书或服务。
> [让 AI 用生活化比喻解释名词](./AI协作排错指南.md#ai-understand-guide)

- **服务器 / ECS**：一台在机房里的、24 小时不关机的电脑。阿里云的 ECS 就是租一台这样的电脑。
- **root / sudo**：root 是服务器的最高管理员；`sudo` 表示“这条命令临时用管理员权限执行”。
- **依赖**：程序运行前需要的配套工具，例如 Python、`curl`、`unzip`。就像打开 Word 文档前，电脑要先装 Word。
- **`.venv` / Python 虚拟环境**：项目自己使用的一套 Python 和依赖目录，避免和系统自带 Python 混在一起。
- **`pip` / PyPI**：`pip` 是 Python 的软件安装命令，PyPI 是它默认访问的软件仓库；网络不通时依赖就下载不了。
- **SHA-256 校验**：给文件计算一串固定“指纹”。上传前后指纹一致，才说明压缩包没有损坏或被替换。
- **包管理器**：Linux 的“应用商店命令”。Ubuntu/Debian 使用 `apt-get`，Alibaba Cloud Linux/CentOS 常用 `dnf` 或 `yum`。
- **配置文件**：保存程序设置的文本文件。修改前要核对路径，改完通常需要重启对应服务。
- **日志**：程序写下的运行记录。排错时要看日志，而不是反复重启碰运气。
- **健康检查 / JSON**：访问一个专门的地址确认程序真的能响应；JSON 是它返回的结构化文字，本项目看到 `"status": "ok"` 才算通过。
- **域名**：门牌号。例如 `www.example.com`。人记域名，电脑记 IP。
- **IP 地址**：电脑在网上的门牌编号，例如 `47.240.12.34`。不好记，所以用域名。
- **DNS / 域名解析**：电话簿。把“域名”翻译成“IP 地址”的服务。
- **NS（Name Server，域名解析服务器）**：电话簿由谁管理。把 NS 改成 Cloudflare，就是让 Cloudflare 替你管电话簿。
- **端口**：一扇编号的门。网页默认走 80（HTTP）和 443（HTTPS）；峰运通服务用 8787；SSH 远程管理用 22。
- **IP 段 / CIDR**：一整片连续的 IP 地址，例如 `173.245.48.0/20`；看到 Cloudflare IP 列表时要把整行原样复制，不要改成单个 IP。
- **安全组**：服务器门口的门卫名单。规定“谁、从哪个方向、能走哪扇门”。
- **入方向 / 出方向**：从外面进服务器叫“入”，服务器主动连外面叫“出”。
- **反向代理 / Caddy**：前台接待员。访客敲 443 号门，Caddy 把他带到内部 8787 号房间，访客并不知道内部房号。
- **Cloudflare**：免费 CDN / 安全平台。域名开启“橙色云代理”后，访客先连接 Cloudflare，再由 Cloudflare 访问服务器。
- **A 记录**：DNS 里最常用的一种记录，把 `fyt.example.com` 指向服务器公网 IPv4 地址。
- **AAAA / CNAME 记录**：AAAA 指向 IPv6 地址；CNAME 把一个域名指向另一个域名。正文传统方案只需要 A 记录，不要凭感觉额外添加。
- **橙色云 / Proxied**：Cloudflare 代理已开启。灰色云表示用户会直接连接服务器，不符合本文推荐配置。
- **Cloudflare Origin CA（源站证书）**：安装在服务器上的 HTTPS 证书，只负责加密“Cloudflare → 服务器”这一段连接。
- **证书 / 私钥**：证书像公开的工作证，私钥像只有本人持有的印章。证书可以公开，私钥绝不能发到群聊、网盘公开链接或 Git。
- **Cloudflare Tunnel（隧道）**：服务器主动向 Cloudflare 建立加密通道，不需要开放入站 80/443；本文把它保留为备选方案。
- **HTTPS**：浏览器地址栏的小锁。数据加密传输，防止被偷看或篡改。
- **systemd / 服务**：服务器的“开机自启 + 守护程序”。峰运通会注册成 `fyt-web` 服务，崩溃自动拉起。
- **部署包**：打包好的整套软件，解压后安装即用。
- **升级补丁**：只包含改动文件的“小包裹”，比整包小、升级快、不影响数据。
- **终端 / 命令行**：黑底白字的窗口，在里面输入命令控制服务器。不要怕，照着复制粘贴即可。

后文反复出现的命令，可以先把它们理解成：

| 命令 | 白话意思 |
| --- | --- |
| `cd 路径` | 进入某个文件夹 |
| `ls` | 看当前文件夹里有什么 |
| `curl 地址` | 从服务器自己访问一个网址，用于检查网络或服务 |
| `nano 文件` | 用简单的终端编辑器打开文件 |
| `systemctl status 名称` | 看一个后台服务是否正在运行 |
| `systemctl restart 名称` | 重启一个后台服务，让新配置生效 |
| `journalctl -u 名称` | 查看这个后台服务的日志和报错 |

安装完成后只需要记住四个固定位置：

| 内容 | 位置 | 日常是否手工修改 |
| --- | --- | --- |
| 程序代码 | `/opt/fyt/server` | 不直接改，用整包或补丁升级 |
| 服务配置 | `/etc/fyt-web/fyt-web.env` | 只有维护人员确认后才改 |
| 账号、数据库、上传文件 | `/var/lib/fyt-web` | **绝不手工删除或覆盖** |
| 备份文件 | `/var/backups/fyt-web` | 定期下载一份到服务器外保存 |

## 0.2 最终架构长什么样

> **可能遇到：**不知道 Cloudflare、Caddy、8787 和数据目录之间如何连接，也不知道故障应先查哪一层。
> [让 AI 帮我看懂整条访问链路](./AI协作排错指南.md#ai-understand-guide)

推荐方案：**传统 A 记录 + Cloudflare 橙色云代理 + Origin CA 源站证书 + Caddy**。

```text
用户浏览器（HTTPS，带小锁）
        │
        ▼
Cloudflare（域名解析、证书、防攻击、隐藏服务器IP）
        │
        │ HTTPS 443（A 记录指向服务器公网 IP）
        ▼
Caddy（监听服务器 443，使用 Cloudflare Origin CA 证书）
        │
        ▼
峰运通 Web 服务（只监听本机 127.0.0.1:8787）
        │
        ▼
数据目录 /var/lib/fyt-web（账号、上传、任务、备份）
```

各层的“为什么”：

1. **峰运通只监听 `127.0.0.1`**：只有同一台服务器上的程序能碰它，外部扫描不到 8787。
2. **Cloudflare A 记录开启橙色云代理**：用户访问 Cloudflare，Cloudflare 再连接服务器公网 IP；不要把记录设成灰色云直连。
3. **Caddy 监听 80/443**：它负责 HTTPS 和反向代理，外部访问不到峰运通内部使用的 8787 端口。
4. **Origin CA + `Full (strict)`**：Cloudflare 会校验服务器证书，访客到 Cloudflare、Cloudflare 到源站两段连接都加密。
5. **安全组只信任 Cloudflare IP 段**：80/443 不向任意来源开放，降低绕过 Cloudflare 直接扫描源站的风险。

> Cloudflare Named Tunnel 仍然可用，适合无法开放 80/443、没有稳定公网 IP，或网络策略不允许传统入站连接的环境。
> 它不再是本文推荐主线，配置方法移到《附录 A：Cloudflare Tunnel 备选方案》。

如果中途看晕，只按下面八个“通过标志”判断，不要靠感觉：

| 顺序 | 通过标志 | 对应位置 |
| --- | --- | --- |
| 1 | Cloudflare 站点显示 `Active` | 第 3 段 |
| 2 | 基础工具全部显示 `[已找到]`，并有 `[Python可用]` | 第 2.5 节 |
| 3 | 安全组没有把 8787 暴露公网 | 第 4 段 |
| 4 | `curl http://127.0.0.1:8787/api/health` 返回 `"status": "ok"` | 第 5.5 节 |
| 5 | Caddy 显示 `active (running)` | 第 6.3 节 |
| 6 | 证书体检显示 `[通过] 证书与私钥配套` | 第 6.4 节 |
| 7 | 手机流量能打开 HTTPS 登录页 | 第 7.3 节 |
| 8 | 重启服务器后 `fyt-web` 和 `caddy` 仍是 `active` | 第 7.5 节 |

# 第 1 段 · 在开发电脑上生成部署包

本项目的打包脚本是现成的：

- `scripts/build_deploy.py`：一次生成**纯净源码包 + Windows 服务端包 + Linux 服务端包**。
- `scripts/build_linux_upgrade_patch.py`：生成 **Linux 增量升级补丁**。

## 1.1 准备一台 Windows 打包电脑

> **可能遇到：**不知道电脑是否合适、软件应该安装在哪里，或安装页面与本文不同。
> [打开“Windows 打包环境”AI 求助入口](./AI协作排错指南.md#ai-build-env)

打包 Windows 服务端包**必须**在 Windows 电脑上进行；Linux 包可以在这台电脑上一起生成。

### 1.1.1 安装 Python 3.13

> **可能遇到：**找不到 64 位安装包、漏选 `Add python.exe to PATH`，或安装后仍找不到 `py`。
> [让 AI 帮我检查 Python 安装](./AI协作排错指南.md#ai-build-env)

1. 打开浏览器访问 `https://www.python.org/downloads/windows/`。
2. 下载 `Python 3.13` 的 **64 位** 安装程序（名字类似 `python-3.13.x-amd64.exe`）。
3. 双击安装。**第一页务必勾选 `Add python.exe to PATH`**（不勾后面命令会找不到 Python）。
4. 一路 Next 到完成。

> **为什么装 Python？**
> 项目后端用 Python 写；打包工具 PyInstaller 也需要 Python。版本必须 3.13，与项目技术基线一致。

### 1.1.2 安装 Node.js（LTS 长期支持版）

> **可能遇到：**不确定哪个是 LTS、安装后 `node`/`npm` 仍不是命令，或版本显示异常。
> [让 AI 帮我检查 Node.js 和 npm](./AI协作排错指南.md#ai-build-env)

1. 打开 `https://nodejs.org/`。
2. 下载 **LTS** 版本（绿色推荐按钮），双击一路下一步。
3. 安装完成后，关闭再重新打开终端。

> **为什么装 Node.js？**
> 网页界面是 React 项目，要用 Node 自带的 `npm` 命令把网页“编译”成静态文件放进部署包。

### 1.1.3 拿到项目源代码

> **可能遇到：**下载后多套一层目录、路径带中文/空格，或不知道是否拿到了完整源码。
> [让 AI 帮我核对源码目录](./AI协作排错指南.md#ai-build-env)

两种方式任选：

- **方式一（推荐）**：向开发同事要项目代码压缩包，解压到 `D:\fyt-src`。
- **方式二**：从 GitHub 下载：打开 `https://github.com/KuroNeko-night/fyt-data-mgmt`，
  点绿色 `Code` → `Download ZIP`，解压后把文件夹重命名为 `D:\fyt-src`。

> **为什么路径用 `D:\fyt-src`？**
> 短、纯英文、没有空格，打包过程最稳。避免中文、空格和过深的目录引发奇怪问题。

### 1.1.4 打开 PowerShell 并检查环境

> **可能遇到：**`cd` 路径不存在，或 `py`、`node`、`npm` 出现“无法识别为命令”。
> [把环境检查结果交给 AI 分析](./AI协作排错指南.md#ai-build-env)

1. 按 `Win` 键，输入 `PowerShell`，回车。
2. 输入以下命令并回车，确认三个软件都在：

```powershell
cd D:\fyt-src
py -3.13 --version
node --version
npm --version
```

每一条都应该打印版本号。如果 `py` 提示找不到，请重新安装 Python 并勾选 Add to PATH。

## 1.2 安装项目依赖

> **可能遇到：**脚本被 PowerShell 阻止、`.venv` 没生成、`npm ci` 下载失败或长时间不动。
> [打开“安装项目依赖”AI 求助入口](./AI协作排错指南.md#ai-build-deps)

在同一个 PowerShell 窗口依次执行（每行输完按回车）：

```powershell
Set-ExecutionPolicy -Scope Process Bypass -Force
$env:PYTHONIOENCODING = "utf-8"
.\scripts\setup-modern.ps1
npm --prefix web-app ci
```

- 第一条：临时允许当前窗口运行项目脚本（只对本窗口生效，不动系统设置）。
- 第二条：让中文输出不乱码。
- 第三条：创建项目专属 Python 环境 `.venv`，并安装 PyInstaller 等打包依赖。
- 第四条：安装网页前端的依赖。

> **为什么先装依赖？**
> `setup-modern.ps1` 会装 `pyinstaller`（把 Python 程序变成 Windows 上的 `.exe`）；
> `npm ci` 会准备网页编译所需的工具。没有它们，打包脚本跑不起来。
> 这步只需做一次；以后重新打包不用重复。

## 1.3 一键生成 Windows + Linux 部署包

> **可能遇到：**进度长时间不变、前端或 PyInstaller 报错、`dist` 缺少某个交付包。
> [打开“生成部署包”AI 求助入口](./AI协作排错指南.md#ai-build-package)

仍在 `D:\fyt-src` 目录执行：

```powershell
.\.venv\Scripts\python.exe scripts\build_deploy.py
```

脚本会自动做四件事：

1. 生成纯净源码包（给开发留档用，部署可以不用）。
2. 自动编译网页前端（内部会调用 `npm run build`）。
3. 用 PyInstaller 打包三个 Windows 程序（**约需几分钟，请耐心等**）。
4. 组装 Linux 部署包，并生成 SHA-256 校验文件。

看到结尾打印 `[完成] Linux 整合包：...` 就是成功了。

打开资源管理器 `D:\fyt-src\dist`，应该看到：

| 文件名 | 用途 | 交给谁 |
| --- | --- | --- |
| `峰运通服务端_windows_v1.3.0.zip` | Windows 电脑上部署的服务器 | 需要 Windows 服务器的同事 |
| `fyt-server-linux-v1.3.0.zip` | Linux 服务器部署包 | 上传到阿里云香港服务器 |
| `fyt-server-linux-v1.3.0.zip.sha256` | Linux 包的校验文件 | 和 Linux 包一起上传，用于验包 |
| `峰运通数据管理系统_源码_v1.3.0.zip` | 纯源码，归档用 | 开发留档 |

> **为什么一个项目要做两个包？**
> Windows 包是“免安装 Python”的绿色包，适合办公室电脑；Linux 包带安装脚本，
> 适合阿里云服务器长期运行、开机自启。两种系统文件不能通用。

### 1.3.1 只生成 Linux 包（更快）

> **可能遇到：**仍然开始构建 Windows 文件，或结束后找不到 Linux 压缩包和 `.sha256`。
> [让 AI 帮我核对 Linux-only 构建](./AI协作排错指南.md#ai-build-package)

如果这次只需要 Linux 包，执行：

```powershell
.\.venv\Scripts\python.exe scripts\build_deploy.py --linux-only
```

会跳过最耗时的 Windows `.exe` 打包，只生成 Linux 包。Windows 包不会重新生成。

### 1.3.2 可选：为 Tunnel 备选方案准备 cloudflared

> **可能遇到：**GitHub 下载超时、镜像失效，或不确定传统公网方案是否可以直接跳过本节。
> [打开“cloudflared 下载”AI 求助入口](./AI协作排错指南.md#ai-build-cloudflared)

Windows 打包时仍会附带 `cloudflared.exe`，供附录 A 的 Tunnel 备选方案或临时测试使用；传统公网方案本身不依赖它。
打包脚本会尝试从 GitHub 下载该客户端，国内网络直接下载可能失败。可以**先**执行项目自带的安装脚本：

```powershell
.\scripts\install-cloudflared.ps1
```

安装成功后它会把客户端放进项目 `tools` 目录，打包脚本会直接复用，不再联网下载。
若加速镜像也失效，可用 `$env:CLOUDFLARED_MIRROR="https://ghfast.top/"` 换一个镜像再试。

## 1.4 把 Windows 包部署到一台 Windows 电脑（简要）

> **可能遇到：**窗口一闪而过、本机能打开但局域网打不开、忘记密码，或升级时担心丢失 `web-data`。
> [打开“Windows 服务端”AI 求助入口](./AI协作排错指南.md#ai-windows-deploy)

Windows 包是绿色免安装包，用于局域网场景。基本流程：

1. 把 `峰运通服务端_windows_v1.3.0.zip` 复制到目标电脑，解压到一个**没有重要资料**的目录（例如 `C:\fyt-server`）。
2. 双击包里的 **`启动服务.bat`**（首次会弹出控制台，要求设置管理员密码：至少 10 位、同时含字母和数字）。
3. 在这台电脑浏览器打开 `http://127.0.0.1:8787`。
4. 局域网其他电脑访问 `http://这台电脑的IP:8787`（若打不开，在 Windows 防火墙放行 8787 端口即可）。
5. 停止服务：双击 **`停止服务.bat`**，或在控制台点“停止”。
6. 忘记管理员密码：先停止服务，在包目录打开 PowerShell，执行 `.\重置管理员密码.ps1`，按提示输入新密码；
   若提示“禁止运行脚本”，先执行 `Set-ExecutionPolicy -Scope Process Bypass -Force` 再重试。
   （该工具随新版包一起重新生成；如果是从旧压缩包直接部署的，请先用第 1 段的流程重新打包。）
7. **升级**：停止服务 → 把旧的 `web-data` 文件夹复制到桌面备份 → 解压新包到新目录 →
   把旧 `web-data` 复制进新目录 → 启动新目录的 `启动服务.bat` → 验证无误后再删旧目录。

> **为什么升级时死保 `web-data`？**
> 账号、上传文件、任务结果全在 `web-data` 里，它才是真正的“数据”；程序文件丢了可以重新解压，数据丢了无法再生。
> 公网正式部署推荐使用 Linux 服务器（本指南重点），Windows 包适合内网快速使用。

# 第 2 段 · 购买域名、域名实名、购买香港服务器（阿里云）

## 2.1 购买域名

> **可能遇到：**不知道该买主域名还是子域名、页面选项和本文不同，或担心误买额外产品。
> [打开“域名购买”AI 求助入口](./AI协作排错指南.md#ai-domain)

1. 打开 `https://wanwang.aliyun.com/`（阿里云万网），登录你的阿里云账号。
   - 若没有账号，先注册；**账号本身也要完成实名认证**（个人上传身份证、企业上传营业执照）。
2. 在搜索框输入你想要的域名，例如 `fyt.example.com` 的前半段，点“查询”。
3. 选一个 **`.com` 结尾**的域名加入购物车，结算。
   - `.com` 最通用，全球解析都顺畅，建议新手首选。
4. 付款前，系统会要求选择“域名信息模板”。点“创建新模板”：
   - 个人：填真实姓名、身份证号，上传身份证照片；
   - 企业：填企业全称、统一社会信用代码，上传营业执照。
5. 用该模板完成购买。

> **为什么域名要实名？**
> 这是中国域名注册的强制要求。不实名，域名会被注册局“锁定/暂停解析”，网站会打不开。
> 模板信息必须真实，提交后一般 1～3 个工作日内审核通过。

## 2.2 等域名实名审核通过

> **可能遇到：**审核不通过、状态长时间不变，或不知道需要补交什么材料。
> [让 AI 帮我看懂实名状态（不要发送证件）](./AI协作排错指南.md#ai-domain)

阿里云控制台 → 域名 → 域名列表，可以看到域名的“实名认证状态”。

- 状态“审核中”：耐心等（通常几小时，最长约 3 天）。
- 状态“已实名”：继续下一步。

> **为什么先实名再配置解析？**
> 未实名的域名可能无法正常解析，后面 Cloudflare 也会提示域名未激活，避免返工。

## 2.3 购买香港区 ECS 服务器

> **可能遇到：**不会选择地域、系统镜像、CPU、内存、带宽或公网 IP。
> [打开“购买服务器”AI 求助入口](./AI协作排错指南.md#ai-ecs)

1. 打开 `https://ecs.console.aliyun.com/`，点“创建实例”。
2. **地域**：选 **中国香港**。
3. **实例规格**：选 `2 vCPU / 2 GiB` 或更高（峰运通是小系统，2 核 2G 足够起步）。
4. **镜像（操作系统）**：选 **Ubuntu 22.04 64 位**（本指南命令以此为准，最省心）。
5. **存储**：系统盘 40 GB ESSD 起步。
6. **公网带宽**：选“按使用流量”，带宽峰值 5 Mbps 起步；文件上传下载多就选更高。
   - 公网 IP 选“分配公网 IPv4 地址”。
7. **登录凭证**：
   - 推荐“密钥对”（安全，像一把只有你有的钥匙）；
   - 新手也可选“自定义密码”，但密码一定要强（12 位以上，大小写+数字+符号），并妥善保存。
8. **购买时长**：先按月买，确认稳定后再按年。
9. 完成支付，等实例状态变为“运行中”。

记录三样东西：**公网 IP、登录用户名（Ubuntu 通常是 `root`）、密码/密钥文件**。

> **为什么选香港区？**
> 中国大陆服务器对外提供网站需要 ICP 备案（周期长、手续多）。香港服务器**不需要备案**，
> 买完就能用，同时离大陆近、网络相对稳定。域名实名仍然要做，但**域名实名 ≠ 备案**。
> 域名续费和服务器续费是两笔钱，记得留意到期时间。

## 2.4 连接服务器（黑窗口终端）

> **可能遇到：**Workbench/SSH 超时、密码或用户名不对，或连接后不知道是否成功。
> [打开“连接服务器”AI 求助入口](./AI协作排错指南.md#ai-ssh)

最省事的方式是用阿里云网页版“Workbench”：

1. 阿里云控制台 → 云服务器 ECS → 实例。
2. 找到你的实例，右侧点“远程连接”。
3. 选择“Workbench 远程连接”，用密码或密钥登录。
4. 登录成功后，就是一个黑底白字的命令行窗口，光标闪烁表示等待输入。

> **为什么用 Workbench？**
> 不用在本地装 SSH 工具，浏览器直接操作服务器；即使你不小心把 22 端口安全规则改坏，Workbench 通常仍能连接（它走阿里云内部通道）。

> 以后你可能会在本地 PowerShell 里用 `ssh root@你的服务器IP` 连接服务器。
> 本指南所有“服务器上执行”的命令，都粘贴到这个黑窗口里，按回车。

## 2.5 第一次登录后，先补齐服务器基础工具

> **可能遇到：**不知道自己的 Linux 属于哪一组、出现 `command not found`、Python 或 `venv` 不可用。
> [打开“Linux 基础工具”AI 求助入口](./AI协作排错指南.md#ai-server-deps)

Linux 部署包包含峰运通程序，但不会把操作系统自己的 Python、解压工具和网络工具塞进压缩包。
这一步相当于先把“剪刀、扳手、螺丝刀”准备好，后面的解压、安装、下载和排错才不会出现 `command not found`。

先执行 `whoami` 看当前登录身份：如果输出 `root`，你已经是最高管理员；若系统又提示 `sudo: command not found`，可把后续命令开头的 `sudo` 去掉。
如果输出不是 `root`，后续必须能使用 `sudo`；没有权限时请改用阿里云 Workbench 的 root 登录，不要尝试绕过权限。

先识别操作系统：

```bash
cat /etc/os-release
```

看输出中的 `NAME=`：

- 包含 `Ubuntu` 或 `Debian`：只执行下面的 **A 组**。
- 包含 `Alibaba Cloud Linux`、`CentOS`、`Rocky` 或 `AlmaLinux`：只执行下面的 **B 组**。
- 不在以上列表：先停止操作，确认系统是否支持 `systemd` 和 Python 3.10～3.13，不要把两组命令都试一遍。

### A 组：Ubuntu / Debian

> **可能遇到：**`apt-get` 报网络、软件源或锁占用错误，安装后仍缺少某个命令。
> [把系统信息和安装错误交给 AI](./AI协作排错指南.md#ai-server-deps)

```bash
sudo apt-get update
sudo DEBIAN_FRONTEND=noninteractive apt-get install -y ca-certificates curl unzip tar gzip nano gnupg openssl sudo iproute2 python3 python3-venv python3-pip
```

### B 组：Alibaba Cloud Linux / CentOS 系

> **可能遇到：**`dnf`/`yum` 不可用、软件包名称不同，或 Python 版本仍不符合要求。
> [让 AI 按当前发行版核对依赖](./AI协作排错指南.md#ai-server-deps)

```bash
sudo dnf makecache
sudo dnf install -y ca-certificates curl unzip tar gzip nano openssl sudo shadow-utils coreutils iproute
sudo dnf install -y python3.13 python3.13-pip \
    || sudo dnf install -y python3.12 python3.12-pip \
    || sudo dnf install -y python3.11 python3.11-pip \
    || sudo dnf install -y python3.10 python3.10-pip
```

这里的 `||` 表示“前一个版本的软件包不存在时，再试下一个版本”。如果系统提示没有 `dnf`、但有 `yum`，把上面的 `dnf` 全部改成 `yum`。
不要卸载或替换系统原有 Python；安装器会在多个版本中选择符合要求的版本，并创建项目自己的 `.venv`。

安装后复制下面的“体检命令”：

```bash
for cmd in systemctl curl unzip tar gzip nano openssl sha256sum ss; do
    if command -v "$cmd" >/dev/null 2>&1; then
        echo "[已找到] $cmd"
    else
        echo "[缺少] $cmd"
    fi
done
for py in python3.13 python3.12 python3.11 python3.10 python3; do
    if command -v "$py" >/dev/null 2>&1 && "$py" -c 'import sys; raise SystemExit(0 if (3,10) <= sys.version_info[:2] <= (3,13) else 1)' 2>/dev/null; then
        echo "[Python可用] $($py --version 2>&1)"
        break
    fi
done
```

正确结果应满足：

- 每个工具前都是 `[已找到]`，不能出现 `[缺少]`。
- 最后至少出现一行 `[Python可用] Python 3.10/3.11/3.12/3.13`。
- 如果没有 `[Python可用]`，先不要执行安装脚本；把 `cat /etc/os-release` 和上面安装命令的最后 30 行错误交给维护人员。

常见提示的意思：

| 屏幕提示 | 意思 | 怎么做 |
| --- | --- | --- |
| `command not found` | 这个工具还没安装，或命令拼错 | 回到本节安装依赖；核对自己执行的是 A 组还是 B 组 |
| `Temporary failure resolving` | 服务器暂时无法解析域名 | 检查安全组出方向 53/80/443 和服务器 DNS，不要反复重装 |
| `Unable to locate package` / `No match for argument` | 软件源里没有这个包 | 先确认系统类型；保留完整报错，不要从陌生网站下载替代包 |
| `systemctl: command not found` | 当前环境没有 systemd | 这通常是容器或极简系统，不符合本部署包要求；更换受支持的 ECS 镜像 |

# 第 3 段 · 把域名解析交给 Cloudflare

## 3.1 注册 Cloudflare 账号

> **可能遇到：**收不到验证邮件、不知道免费方案是否够用，或页面菜单名称变化。
> [打开“Cloudflare 与 NS”AI 求助入口](./AI协作排错指南.md#ai-nameserver)

1. 打开 `https://dash.cloudflare.com/sign-up`。
2. 用邮箱注册，设置强密码，**强烈建议开启两步验证**（账号安全里）。
3. 登录后点“Add a site（添加站点）”，输入你购买的**根域名**，例如访问地址准备使用 `fyt.example.com`，这里应填写 `example.com`。

> **为什么用 Cloudflare？**
> 免费套餐包含域名解析、边缘 HTTPS、橙色云代理和基础防护；Cloudflare Origin CA 还能为“Cloudflare → 服务器”提供可严格校验的源站证书。
> 解析生效速度通常比改阿里云解析更快、更稳定。
> 小提示：Cloudflare 免费版在大陆个别时段/地区访问速度可能有波动；如业务用户全部在大陆且对速度敏感，
> 后续再与开发同事评估其他加速方案即可，本指南流程不受影响。

## 3.2 Cloudflare 会给两个 NS 地址

> **可能遇到：**找不到两个 NS、复制时漏字符，或误以为它们是 A 记录。
> [让 AI 帮我区分 NS 与 DNS 记录](./AI协作排错指南.md#ai-nameserver)

添加站点后，Cloudflare 免费计划 → Continue → 它会扫描现有解析记录并给你**两个 NS 地址**，
样子类似：

```text
amy.ns.cloudflare.com
cody.ns.cloudflare.com
```

**把这两个地址抄下来。**

## 3.3 回阿里云修改域名解析服务器（NS）

> **可能遇到：**找不到“修改 DNS 服务器”、阿里云不接受输入，或旧 NS 没有被替换。
> [打开“修改 NS”AI 求助入口](./AI协作排错指南.md#ai-nameserver)

1. 阿里云控制台 → 域名 → 域名列表。
2. 找到你的域名，点“管理”。
3. 左侧找 **“DNS 修改” / “修改 DNS 服务器”**（不同时期菜单名略有差异）。
4. 删除阿里云默认的 `dnsXX.hichina.com`，填入 Cloudflare 给的两个 NS 地址，保存。

> **为什么要改 NS？**
> 域名注册商（阿里云）负责“登记”，但解析工作可以委托给 Cloudflare。
> 改 NS 就是告诉全球互联网：“以后查这个域名，去问 Cloudflare”。域名所有权和续费仍在阿里云。

## 3.4 等待生效

> **可能遇到：**Cloudflare 长时间显示 `Pending`，不知道该继续等待还是设置错误。
> [让 AI 根据状态和等待时间判断](./AI协作排错指南.md#ai-nameserver)

1. 回 Cloudflare 面板，点 “Done, check nameservers”。
2. 状态从 `Pending Nameserver Update` 变为 `Active` 需要几分钟到 24 小时（通常很快，可先做服务器部署）。
3. 不生效时，过几小时再回来点 “Check nameservers”。

> **为什么要等？**
> NS 变更要一层层通知全球 DNS 服务器，就像修改门牌号后要给所有快递点发通知，需要传播时间。

进入下一段前只看一个结果：Cloudflare 站点状态应为 **Active**。如果仍是 Pending，可以先安装服务器，但第 7 段的公网访问不会成功，不要把它误判成 Caddy 故障。

# 第 4 段 · 设置服务器出入站安全策略（安全组）

## 4.1 先理解方向

> **可能遇到：**分不清入方向/出方向，或不知道端口规则保护的是哪一段连接。
> [让 AI 用门卫比喻解释安全组](./AI协作排错指南.md#ai-security-group)

- **入方向规则**：管“外面的人能不能进服务器”。例如别人连你的 22 端口、80 端口。
- **出方向规则**：管“服务器能不能主动连外面”。例如服务器下载系统更新、Python 依赖和安全补丁。
- 安全组是“白名单”逻辑：**只有明确允许的才放行，其余默认全部拒绝**（入方向）。
- 阿里云默认的安全组往往开放较多端口，**务必按下面改成最小权限**。

## 4.2 推荐方案（传统解析）的安全组规则

> **可能遇到：**现有规则很多、不知道哪些要保留，或担心把 8787 错误开放到公网。
> [打开“传统方案安全组”AI 求助入口](./AI协作排错指南.md#ai-security-group)

在阿里云控制台：ECS 实例 → 安全组 → 配置规则 → 入方向 / 出方向。

### 入方向（外面 → 服务器）

> **可能遇到：**Cloudflare IP 段不会填、22 端口来源不会限制，或规则提示重复/冲突。
> [让 AI 逐条核对入方向规则](./AI协作排错指南.md#ai-security-group)

| 优先级 | 协议类型 | 端口范围 | 授权对象（来源） | 为什么这样设 |
| --- | --- | --- | --- | --- |
| 1 | SSH(22) | 22/22 | `你的常用公网IP/32` | 只允许你自己的电脑远程管理服务器 |
| 2 | 全部 ICMP(IPv4) | -1/-1 | `你的常用公网IP/32`（可选） | 只允许你自己 ping 测网络 |
| 3 | TCP | 80/80 | Cloudflare IPv4/IPv6 地址段（逐条添加） | 只接收 Cloudflare 的 HTTP 请求和 HTTPS 跳转 |
| 4 | TCP | 443/443 | Cloudflare IPv4/IPv6 地址段（逐条添加） | 只接收 Cloudflare 转发的 HTTPS 请求 |

Cloudflare 官方 IP 段列表：`https://www.cloudflare.com/ips/`。如果本服务器只使用公网 IPv4（本指南默认情况），只添加官方页面中的 IPv4 段；
只有同时配置了公网 IPv6 和 AAAA 记录时，才添加 IPv6 段。每个 IP 段分别添加两条规则：一条 TCP 80、一条 TCP 443。
以后 Cloudflare 更新地址段时也要同步安全组。**80、443 的来源不要填写 `0.0.0.0/0`，8787 永远不对公网开放。**

> 自己的公网 IP 可以在百度搜索“IP”查看；家庭宽带 IP 变了登录不上时，回控制台更新这个 IP。
> 如果只用阿里云 Workbench 管理服务器，连 22 也可以先不开放——少开一扇门，少一分风险。

### 出方向（服务器 → 外面）

> **可能遇到：**服务器无法下载依赖、DNS 解析失败，或不知道 53/80/443 应如何放行。
> [让 AI 逐条核对出方向规则](./AI协作排错指南.md#ai-security-group)

| 优先级 | 协议类型 | 端口范围 | 授权对象（目的地） | 为什么需要 |
| --- | --- | --- | --- | --- |
| 1 | TCP | 80/80 | 0.0.0.0/0 | 系统更新和部分软件下载走 HTTP |
| 2 | TCP | 443/443 | 0.0.0.0/0 | HTTPS 下载、pip 安装依赖和系统更新 |
| 3 | UDP | 53/53 | 0.0.0.0/0 | DNS 查询（把域名翻译成 IP） |
| 4 | TCP | 53/53 | 0.0.0.0/0 | DNS 查询的兜底通道 |

> **为什么出方向还要管？**
> 如果服务器被入侵，限制出方向能阻止它随意连接陌生地址、下载木马或对外攻击。
> 这几条规则覆盖了推荐方案用到的正常外连：更新、下载和 DNS。
> 若某些步骤下载失败，优先怀疑漏了 80/443 出方向规则。

## 4.3 Tunnel 备选方案的差异（只在使用附录 A 时看）

> **可能遇到：**不确定自己是否在用 Tunnel，或不知道 7844 是否需要开放。
> [打开“Tunnel 备选方案”AI 求助入口](./AI协作排错指南.md#ai-tunnel)

若采用附录 A 的 Tunnel：入方向不需要开放 80/443；出方向除了上表规则，还需允许 UDP 7844 和 TCP 7844 到 `0.0.0.0/0`。
不要同时长期运行传统公网入口和 Tunnel，除非你明确需要双入口并理解相应的访问控制与排错成本。

## 4.4 检查服务器自身的防火墙

> **可能遇到：**不知道服务器使用 `ufw` 还是 `firewalld`，安全组已开放但请求仍进不来。
> [打开“服务器防火墙”AI 求助入口](./AI协作排错指南.md#ai-firewall)

阿里云安全组是“服务器外面的门卫”，Ubuntu 的 `ufw` 或 Alibaba Cloud Linux 的 `firewalld` 是“服务器里面的第二道门”。
如果第二道门仍然关闭，即使安全组已放行，Caddy 也收不到请求。

先查看哪一种防火墙正在运行：

```bash
sudo ufw status 2>/dev/null || true
sudo firewall-cmd --state 2>/dev/null || true
```

- 如果看到 `Status: inactive` 或 `not running`，不用为了本指南额外安装防火墙。
- 如果 `ufw` 显示 `active`，执行：

  ```bash
  sudo ufw allow 80/tcp
  sudo ufw allow 443/tcp
  sudo ufw reload
  ```

- 如果 `firewalld` 显示 `running`，执行：

  ```bash
  sudo firewall-cmd --permanent --add-service=http
  sudo firewall-cmd --permanent --add-service=https
  sudo firewall-cmd --reload
  ```

这里允许的是服务器本地防火墙的 80/443；外部来源仍由上一节的阿里云安全组限制为 Cloudflare IP 段。

进入下一段前按这张清单核对：

- 22：只允许自己的公网 IP，或者只使用 Workbench。
- 80/443：只允许 Cloudflare 官方 IPv4 段。
- 8787：没有任何公网入方向规则。
- 出方向：至少允许 DNS 53、HTTP 80、HTTPS 443。
- 本机防火墙若正在运行，已放行 HTTP/HTTPS。

# 第 5 段 · 把 Linux 包部署到服务器

## 5.1 上传 Linux 部署包

> **可能遇到：**Workbench 上传中断、服务器中找不到文件，或部署包与 `.sha256` 没有一起上传。
> [打开“上传部署包”AI 求助入口](./AI协作排错指南.md#ai-upload)

**方式一：Workbench 上传（新手推荐）**

1. 在阿里云 Workbench 连接窗口上方找“文件上传/发送文件”按钮（图标常为向上箭头）。
2. 同时上传 `fyt-server-linux-v1.3.0.zip` 和 `fyt-server-linux-v1.3.0.zip.sha256` 两个文件。
3. 上传默认落在 `/root` 目录。

**方式二：本地 PowerShell 用 scp 上传**

```powershell
scp D:\fyt-src\dist\fyt-server-linux-v1.3.0.zip root@你的服务器公网IP:/root/
scp D:\fyt-src\dist\fyt-server-linux-v1.3.0.zip.sha256 root@你的服务器公网IP:/root/
```

> 方式二要求 22 端口对你自己 IP 开放。两种方式结果一样。

## 5.2 核对压缩包是否完整（防损坏/防篡改）

> **可能遇到：**显示 `FAILED`、找不到校验文件，或文件名和校验记录不一致。
> [打开“文件校验”AI 求助入口](./AI协作排错指南.md#ai-checksum)

`.sha256` 是构建时生成的“文件指纹”。在服务器执行：

```bash
cd /root
sha256sum -c fyt-server-linux-v1.3.0.zip.sha256
```

看到 `fyt-server-linux-v1.3.0.zip: OK` 或“确定”才继续。不通过就删除服务器上的两个文件并重新上传，不能跳过校验硬装。

> **为什么要验？**
> 网络传输可能丢字节，文件损坏后安装会报莫名错误。SHA-256 校验就像包裹上的“防拆封条”，能确认收到的文件与打包时完全一致。

## 5.3 解压

> **可能遇到：**没有 `unzip`、权限不足、目录套了多层，或解压后找不到 `install.sh`。
> [打开“解压部署包”AI 求助入口](./AI协作排错指南.md#ai-extract)

```bash
cd /root
sudo mkdir -p /opt/fyt
sudo unzip fyt-server-linux-v1.3.0.zip -d /opt/fyt
cd /opt/fyt/fyt-server-linux-v1.3.0
ls
```

`ls` 应能看到：`install.sh`、`web_server.py`、`web_backend`、`core`、`web-app`、`requirements.txt`、`fyt-web.service` 以及 `*.sh` 运维脚本。

> **为什么解压到 /opt/fyt？**
> `/opt` 是 Linux 放“额外安装的软件”的标准目录；`/opt/fyt` 是项目固定根目录。
> 包从中文目录、`/root` 都能解压，但正式运行目录必须是 ASCII 路径，安装器会自动处理。

## 5.4 执行一键安装

> **可能遇到：**依赖下载长时间不动、`.venv` 创建失败、服务注册失败，或没有保存一次性管理员密码。
> [打开“一键安装”AI 求助入口](./AI协作排错指南.md#ai-install)

**方式一（推荐）：让安装器生成随机初始密码**

```bash
sudo env FYT_WEB_HOST=127.0.0.1 bash install.sh
```

安装过程中会打印一次随机管理员密码。立即保存到密码管理器；建库成功后，安装器会把这条初始密码从服务器配置中删除。

**方式二：自己设置密码，但不要把密码直接写进命令**

```bash
read -s -p "请输入管理员初始密码（至少10位，含字母和数字）: " FYT_ADMIN_PASSWORD
echo
sudo env FYT_WEB_HOST=127.0.0.1 FYT_ADMIN_PASSWORD="$FYT_ADMIN_PASSWORD" bash install.sh
unset FYT_ADMIN_PASSWORD
```

输入密码时屏幕不会出现字符，这是正常的。这样终端历史只记录变量名，不记录实际密码。

- `FYT_WEB_HOST=127.0.0.1`：让峰运通只监听本机，只能由同一台服务器上的 Caddy 访问。
- 管理员密码要求 **10～128 位，并同时包含字母和数字**；不要使用文档示例、公司名或连续数字。

> **为什么用 `sudo env ... bash install.sh`？**
> 安装要创建系统账号、写系统目录、注册开机自启服务，必须有管理员权限（sudo）。
> `env` 只把指定设置交给这一次安装过程，不会永久改变系统其他程序的环境。

安装器会自动完成（这就是“为什么这样设计”的意义）：

| 动作 | 为什么 |
| --- | --- |
| 创建低权限账号 `fyt-web` | 不让系统程序用 root 跑，被攻击时损失更小 |
| 创建私有 Python 虚拟环境 | 不污染系统 Python，升级版本互相隔离 |
| 安装锁定依赖 | 保证服务器和测试环境版本一致 |
| 创建 `/var/lib/fyt-web` 数据目录 | 程序和数据分开，升级程序时不碰数据 |
| 写 `/etc/fyt-web/fyt-web.env` 配置 | 配置固定一处，好查好改 |
| 注册 `fyt-web` systemd 服务 | 开机自启、崩溃自动拉起 |
| 安装前备份旧数据 | 升级失败可回退 |
| 健康检查 `/api/health` | 确认服务真的能工作，不只是进程存在 |
| 成功后删除初始密码 | 密码不会长期留在配置文件里 |

安装依赖时几分钟没有新输出并不一定是卡死，尤其是首次下载 Python 软件包时。不要关闭终端；只有出现 `[错误]` 或长时间完全没有网络流量时才开始排查。

看到 `[安装完成]` 后，服务已经运行。如果失败，先按错误文字判断：

| 错误中包含 | 常见原因 | 处理方法 |
| --- | --- | --- |
| `Permission denied` / `请使用 sudo` | 没有管理员权限 | 确认命令以 `sudo ... bash install.sh` 开头 |
| `未找到 Python 3.10+` | 系统 Python 太旧或软件源缺包 | 回到 2.5 节；不要替换系统 Python，可用 `FYT_PYTHON=/完整路径/python3.11` 指定新版本 |
| `No module named venv` / `创建虚拟环境失败` | Python 的 venv 组件缺失 | Ubuntu 执行 `sudo apt-get install -y python3-venv`；其他系统重新安装对应版本 Python 包 |
| `pip`、`Read timed out`、`Connection` | Python 依赖下载失败 | 检查出方向 53/80/443；网络较慢时用下方镜像命令重新执行 |
| `部署包缺少必要文件` | 压缩包不完整或进入了错误目录 | 重新核对 5.2 校验值和 5.3 的 `ls` 输出 |

网络较慢时可以安全地重新运行安装器，并临时指定阿里云 Python 镜像：

```bash
sudo env FYT_WEB_HOST=127.0.0.1 PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/ bash install.sh
```

安装脚本会先在暂存目录准备新版本，成功前不会直接覆盖正在运行的旧程序；重复执行不是“安装两份”。

## 5.5 确认服务正常

> **可能遇到：**`fyt-web` 不是 `active`、8787 拒绝连接、健康检查没有返回 `"status": "ok"`。
> [打开“峰运通服务健康检查”AI 求助入口](./AI协作排错指南.md#ai-app-health)

```bash
sudo bash /opt/fyt/server/status.sh
curl http://127.0.0.1:8787/api/health
```

`status.sh` 末尾显示 `[正常]`；`curl` 返回一段 JSON，其中包含 `"status": "ok"` 即成功。

如果显示 `Connection refused`，说明 8787 没有程序监听；执行：

```bash
sudo systemctl status fyt-web --no-pager
sudo bash /opt/fyt/server/logs.sh 100
```

先解决日志中的第一条错误。**只有本节健康检查通过，才继续安装 Caddy。**

> **为什么现在只能本机访问？**
> 我们故意让它只监听 `127.0.0.1`，此时还没有配置 Caddy 公网入口。下一段继续完成 HTTPS。

## 5.6 日常必会的六个命令

> **可能遇到：**不知道该查看状态、重启还是看日志，或担心命令会影响正在使用系统的人。
> [让 AI 帮我选择最安全的项目命令](./AI协作排错指南.md#ai-linux-ops)

```bash
sudo bash /opt/fyt/server/status.sh          # 看服务状态 + 健康检查
sudo bash /opt/fyt/server/restart.sh         # 重启服务
sudo bash /opt/fyt/server/stop.sh            # 停止服务
sudo bash /opt/fyt/server/start.sh           # 启动服务
sudo bash /opt/fyt/server/logs.sh 100        # 看最近 100 行日志
sudo bash /opt/fyt/server/backup.sh          # 备份数据（会短暂停服务，很快）
```

# 第 6 段 · 安装 Caddy，配置源站 HTTPS

## 6.1 为什么需要 Caddy

> **可能遇到：**不理解为什么峰运通已经在 8787 运行，还需要 Caddy 和 443。
> [让 AI 用白话解释 Caddy 这一层](./AI协作排错指南.md#ai-caddy-overview)

峰运通跑在内部端口 8787。直接把它暴露公网会绕过 Cloudflare，也缺少专门的 HTTPS 和反向代理层。
Caddy 监听 **80/443**，使用 Cloudflare Origin CA 证书接收 Cloudflare 的 HTTPS 请求，再转给 8787：

```text
Cloudflare → 服务器公网 IP:443 (Caddy) → 127.0.0.1:8787 (峰运通)
```

Caddy 还是未来扩展的“总门卫”：以后想挂第二个网站、加访问密码、看请求日志，都改 Caddy 一处即可。

## 6.2 安装 Caddy

> **可能遇到：**`caddy: command not found`、软件源添加失败，或不知道该执行 A 组还是 B 组。
> [打开“安装 Caddy”AI 求助入口](./AI协作排错指南.md#ai-caddy-install)

先检查服务器是否已经安装：

```bash
if command -v caddy >/dev/null 2>&1; then
    echo "[已安装] $(caddy version)"
else
    echo "[未安装] 请按当前操作系统执行下面对应的一组命令"
fi
```

已经显示 `[已安装]` 可以直接进入 6.3。未安装时，先用 `cat /etc/os-release` 确认系统，然后**只执行匹配的一组**。

### A 组：Ubuntu / Debian 安装 Caddy

> **可能遇到：**`apt-get`、密钥或软件源命令失败，安装后没有 `caddy.service`。
> [让 AI 按 Ubuntu/Debian 官方路线检查](./AI协作排错指南.md#ai-caddy-install)

```bash
sudo apt-get update
sudo apt-get install -y debian-keyring debian-archive-keyring apt-transport-https ca-certificates curl gnupg
curl -fsSL 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor --yes -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -fsSL 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list >/dev/null
sudo apt-get update
sudo apt-get install -y caddy
```

### B 组：Alibaba Cloud Linux 3 / CentOS Stream 9 系安装 Caddy

> **可能遇到：**COPR/软件仓库不支持当前发行版，或系统找不到 Caddy 软件包。
> [让 AI 判断当前系统是否受官方仓库支持](./AI协作排错指南.md#ai-caddy-install)

```bash
sudo dnf install -y 'dnf-command(copr)'
sudo dnf copr enable -y @caddy/caddy
sudo dnf install -y caddy
```

如果 B 组提示当前发行版没有可用的 Caddy 仓库，不要从不明下载站随便找二进制文件。对零基础维护者，最稳妥的处理是按第 2.3 节使用 Ubuntu 22.04/24.04 服务器；必须保留现有系统时，再让维护人员按 Caddy 官方发布包单独配置服务账号和 systemd 单元。

> **什么叫“软件源”？**
> 它是系统信任的软件下载地址，类似手机应用商店。先添加 Caddy 官方软件源，再用 `apt-get` 或 `dnf` 安装，后续系统更新时才能一起收到安全更新。

## 6.3 确认 Caddy 真的安装完整

> **可能遇到：**服务不存在、`caddy` 账号/组不存在、80/443 被其他程序占用，或状态为 `failed`。
> [打开“Caddy 完整性检查”AI 求助入口](./AI协作排错指南.md#ai-caddy-service)

```bash
command -v caddy
caddy version
getent passwd caddy
getent group caddy
sudo systemctl enable --now caddy
sudo systemctl status caddy --no-pager
```

正确结果应同时满足：

1. `command -v caddy` 返回类似 `/usr/bin/caddy`。
2. `caddy version` 返回版本号，而不是 `command not found`。
3. `getent passwd caddy` 和 `getent group caddy` 都有一行输出，说明安装包创建了低权限服务账号和组。
4. 最后一项显示 `active (running)`。

如果失败，不要继续创建证书文件，因为后续的 `root:caddy` 权限依赖这个账号和组：

| 提示 | 原因 | 处理方法 |
| --- | --- | --- |
| `gpg: command not found` | 缺少签名校验工具 | Ubuntu/Debian 执行 `sudo apt-get install -y gnupg` 后重试 A 组 |
| `Could not resolve` / `Connection timed out` | DNS 或出方向网络不通 | 检查安全组出方向 53/80/443，并测试 `curl -I https://dl.cloudsmith.io` |
| `caddy: command not found` | 安装命令没有成功执行到最后 | 回看安装输出中的第一条错误，不要手工创建一个同名空文件 |
| `Unit caddy.service not found` | 只下载了二进制或软件包安装不完整 | 重新执行对应安装组；确认最后一条安装命令成功 |
| `failed` / `exit-code` | 服务启动失败 | 执行 `sudo journalctl -u caddy -n 80 --no-pager`，保留完整输出再排错 |

## 6.4 在 Cloudflare 创建 Origin CA 源站证书

> **可能遇到：**分不清证书和私钥、粘贴不完整、两者不配套，或 Caddy 没权限读取 `.key`。
> [打开“Origin CA 证书”AI 求助入口（不要发送私钥）](./AI协作排错指南.md#ai-certificate)

1. 打开 Cloudflare 面板 → 选择你的域名 → `SSL/TLS` → `Origin Server`。
2. 点 `Create Certificate`，主机名至少包含 `fyt.example.com`；其余选项保持默认即可。
3. Cloudflare 会显示**证书**和**私钥**。证书以后还能查看，私钥通常只显示这一次，先分别保存到自己电脑的临时文本文件。
4. 不要把证书私钥发到群聊、写进本文、放进源码包或提交 Git。

在服务器创建证书目录：

```bash
sudo install -d -m 750 -o root -g caddy /etc/caddy/certs
sudo touch /etc/caddy/certs/fyt.example.com.pem /etc/caddy/certs/fyt.example.com.key
sudo chown root:caddy /etc/caddy/certs/fyt.example.com.pem /etc/caddy/certs/fyt.example.com.key
sudo chmod 640 /etc/caddy/certs/fyt.example.com.pem /etc/caddy/certs/fyt.example.com.key
```

把 Cloudflare 显示的完整证书（含 `BEGIN CERTIFICATE` 和 `END CERTIFICATE`）放进：

```bash
sudo nano /etc/caddy/certs/fyt.example.com.pem
```

把完整私钥（含 `BEGIN PRIVATE KEY` 和 `END PRIVATE KEY`）放进：

```bash
sudo nano /etc/caddy/certs/fyt.example.com.key
```

`nano` 中粘贴后按 `Ctrl+O`（字母 O）、回车保存，再按 `Ctrl+X` 退出。前面的 `chmod 640` 已经在写入内容前限制了读取权限；最后再核对一次：

```bash
sudo chown root:caddy /etc/caddy/certs/fyt.example.com.pem /etc/caddy/certs/fyt.example.com.key
sudo chmod 640 /etc/caddy/certs/fyt.example.com.pem /etc/caddy/certs/fyt.example.com.key
sudo ls -l /etc/caddy/certs/
```

两行文件权限应以 `-rw-r-----` 开头，所有者和组应为 `root caddy`。这表示只有 root 能修改，Caddy 服务只能读取，其他用户无权查看私钥。

再执行一次证书体检。它只计算公开信息的摘要，不会显示私钥内容：

```bash
sudo openssl x509 -in /etc/caddy/certs/fyt.example.com.pem -noout -subject -issuer -dates
CERT_KEY=$(sudo openssl x509 -in /etc/caddy/certs/fyt.example.com.pem -pubkey -noout | openssl sha256)
PRIVATE_KEY=$(sudo openssl pkey -in /etc/caddy/certs/fyt.example.com.key -pubout | openssl sha256)
echo "证书公钥: $CERT_KEY"
echo "私钥公钥: $PRIVATE_KEY"
if [ "$CERT_KEY" = "$PRIVATE_KEY" ]; then echo "[通过] 证书与私钥配套"; else echo "[失败] 证书与私钥不是一对"; fi
unset CERT_KEY PRIVATE_KEY
```

必须看到 `[通过] 证书与私钥配套`。如果显示证书无法读取，通常是漏了开头/结尾行；如果两个摘要不同，说明证书与私钥来自不同的一次创建操作，需要在 Cloudflare 重新创建一套，不能拼在一起使用。

> Cloudflare Origin CA 证书是给 Cloudflare 连接源站使用的。直接访问服务器 IP 时，浏览器不信任它是正常现象；正式用户必须通过开启橙色云代理的域名访问。

## 6.5 写 Caddy 配置（443 转给 8787）

> **可能遇到：**忘记替换域名、证书路径错误、配置校验失败，或本机 HTTPS 返回 502。
> [打开“Caddyfile 配置”AI 求助入口](./AI协作排错指南.md#ai-caddyfile)

先把下面三处 `fyt.example.com` 全部换成你的真实访问域名，再把整个代码框一次性复制到服务器终端。开头和结尾的 `EOF` 是“配置内容从这里开始/结束”的标记，也必须一起复制：

```bash
sudo mkdir -p /etc/caddy
sudo tee /etc/caddy/Caddyfile >/dev/null <<'EOF'
fyt.example.com {
    tls /etc/caddy/certs/fyt.example.com.pem /etc/caddy/certs/fyt.example.com.key
    encode gzip
    reverse_proxy 127.0.0.1:8787
}
EOF
sudo caddy fmt --overwrite /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl restart caddy
sudo systemctl status caddy --no-pager
```

说明：

- `fyt.example.com`：Caddy 为这个域名监听 HTTPS，并把 HTTP 自动跳转到 HTTPS。
- `tls ...pem ...key`：明确使用刚创建的 Cloudflare Origin CA 证书和私钥，不让 Caddy 向公共证书机构申请证书。
- `reverse_proxy 127.0.0.1:8787`：把请求转给峰运通。
- `caddy validate`：在重启前检查配置；`systemctl status caddy` 应显示 `active (running)`。

检查三个端口分别由谁监听：

```bash
sudo ss -lntp | grep -E ':(80|443|8787)\b'
```

正常情况下：

- 8787 只应出现在 `127.0.0.1:8787`，不能是 `0.0.0.0:8787`。
- 80 和 443 应由 Caddy 监听；显示 `0.0.0.0`、`*` 或 `[::]` 均表示在接收外部连接。
- 443 没出现：先看 `sudo journalctl -u caddy -n 80 --no-pager`，不要继续配置 DNS。

本机自测 Caddy 是否转达成功：

```bash
curl -vk --resolve fyt.example.com:443:127.0.0.1 https://fyt.example.com/api/health
```

返回包含 `"status": "ok"` 的 JSON，说明“Caddy HTTPS → 8787”已经连通。`-k` 只用于这次本机自测，正式浏览器访问不需要也不能关闭证书校验。

# 第 7 段 · 添加传统 DNS 解析，开放公网

## 7.1 在 Cloudflare 添加 A 记录

> **可能遇到：**根域/子域不会填、A 记录指向旧 IP、同名 A/AAAA/CNAME 冲突，或橙色云没开启。
> [打开“A 记录与橙色云”AI 求助入口](./AI协作排错指南.md#ai-dns-a)

先确认第 3 段 Cloudflare 面板里的域名状态已经是 **Active**，然后进入：域名 → `DNS` → `Records` → `Add record`。

| 项目 | 填什么 | 说明 |
| --- | --- | --- |
| Type | `A` | 表示域名指向一个 IPv4 地址 |
| Name | `fyt` | 最终地址为 `fyt.example.com`；若要使用根域名则填 `@` |
| IPv4 address | 服务器公网 IP | 必须填阿里云 ECS 的公网地址，不是 `127.0.0.1` 或内网地址 |
| Proxy status | **Proxied（橙色云朵）** | 用户先连接 Cloudflare，不能设成灰色云直连 |
| TTL | `Auto` | 交给 Cloudflare 自动管理 |

如果相同主机名已经有 Tunnel 自动创建的 CNAME 记录，先确认旧 Tunnel 不再使用，再删除冲突的 CNAME，然后添加 A 记录。
同一名称不要同时保留错误的 AAAA 记录；只有服务器确实配置了公网 IPv6、Caddy 和安全组也支持 IPv6 时才添加 AAAA。

> A 记录会保存服务器公网 IP，但开启橙色云代理后，普通 DNS 查询返回的是 Cloudflare 地址。服务器真实 IP 仍可能通过历史记录或其他渠道被发现，所以安全组必须继续只允许 Cloudflare IP 段访问 80/443。

## 7.2 设置 Cloudflare HTTPS 模式

> **可能遇到：**不知道应该选哪个模式，或改成 `Full (strict)` 后出现 525/526。
> [打开“Cloudflare HTTPS 模式”AI 求助入口](./AI协作排错指南.md#ai-cloudflare-tls)

进入 Cloudflare → `SSL/TLS` → `Overview`，把加密模式设置为 **Full (strict)**。

- 不要选择 `Flexible`：它会让 Cloudflare 到服务器这一段退化为明文 HTTP。
- 不要长期使用普通 `Full`：它不严格校验源站证书。
- `Full (strict)` 会验证第 6 段安装的 Origin CA 证书是否有效、是否匹配当前域名。

可在 `SSL/TLS` → `Edge Certificates` 开启 `Always Use HTTPS`，让 Cloudflare 侧也把 HTTP 请求跳转到 HTTPS；Caddy 的自动跳转仍作为源站兜底。

## 7.3 按顺序验证整条链路

> **可能遇到：**服务器本机正常但手机打不开，或看到 404、502、522、525、526、白页等现象。
> [打开“公网访问分层排查”AI 求助入口](./AI协作排错指南.md#ai-public-access)

先在服务器确认两个服务都正常：

```bash
sudo systemctl status fyt-web --no-pager
sudo systemctl status caddy --no-pager
curl http://127.0.0.1:8787/api/health
curl -vk --resolve fyt.example.com:443:127.0.0.1 https://fyt.example.com/api/health
```

前两项应显示 `active (running)`，两个 `curl` 都应返回包含 `"status": "ok"` 的 JSON。

然后断开手机 Wi-Fi，使用移动网络打开 `https://fyt.example.com`：

1. 应出现峰运通登录页，地址栏有小锁。
2. 登录后检查工作台和任一业务页面能否正常打开。
3. 第一次公网验收完成后，立即在“账号安全”中确认管理员密码和登录设备。

> 手机流量能绕开公司或家庭网络的 DNS 缓存，更接近真实外部用户。如果服务器本机两次 `curl` 都正常而公网打不开，优先检查 Cloudflare A 记录、橙色云状态、`Full (strict)`、安全组 80/443 来源和 Caddy 日志。

## 7.4 Caddy 的日常命令

> **可能遇到：**修改配置后不知道该 reload 还是 restart，或担心重启前没有检查语法。
> [让 AI 帮我安全地让 Caddy 配置生效](./AI协作排错指南.md#ai-caddy-ops)

```bash
sudo systemctl status caddy --no-pager             # 查看 Caddy 状态
sudo systemctl restart caddy                       # 修改配置或证书后重启
sudo journalctl -u caddy -n 50 --no-pager          # 查看最近 50 行日志
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile  # 重启前检查配置
```

服务器公网 IP 发生变化时，需要先修改 Cloudflare A 记录，再验证安全组和公网访问。Cloudflare 官方 IP 段发生变化时，也要同步更新阿里云安全组。

## 7.5 最后做一次重启验收

> **可能遇到：**重启后远程连接暂时断开、服务没有自动启动，或网站变成 502/525。
> [打开“服务器重启后验收”AI 求助入口](./AI协作排错指南.md#ai-reboot)

公网首次测试通过后，在业务空闲时重启服务器，确认峰运通和 Caddy 都能开机自动启动：

```bash
sudo reboot
```

终端连接立即断开是正常现象。等待约 1～3 分钟，重新进入 Workbench，再执行：

```bash
sudo systemctl is-enabled fyt-web caddy
sudo systemctl is-active fyt-web caddy
curl http://127.0.0.1:8787/api/health
```

前两项应分别显示 `enabled` 和 `active`，健康检查应包含 `"status": "ok"`。最后再用手机流量打开公网域名；这一步通过后，首次部署才算真正完成。

# 第 8 段 · 生成升级补丁并应用到服务器

## 8.1 什么时候用“补丁”，什么时候用“整包”

> **可能遇到：**不知道本次改动属于补丁还是整包，或担心升级会碰到现有账号和数据。
> [让 AI 先帮我判断升级方式](./AI协作排错指南.md#ai-upgrade-choice)

| 改动内容 | 用哪个 |
| --- | --- |
| 只改了后端代码 `web_server.py` / `web_backend/` | **补丁** |
| 只改了业务核心 `core/*.py` | **补丁** |
| 只改了网页前端 `web-app/` | **补丁** |
| 改了运行依赖 `requirements-runtime.txt` | **补丁**（补丁脚本会顺带更新依赖） |
| 改了 `packaging/linux/` 下的安装/运维脚本或 `fyt-web.service` | **整包重新安装** |
| 大版本升级、数据结构变更 | **整包重新安装 + 人工核验** |

> **为什么分两种？**
> 补丁只有几百 KB 到几 MB，上传快、停服时间短；整包包含所有文件，适合“家底”变更。
> 补丁**永远不会**读取、复制、删除 `/var/lib/fyt-web` 数据，设计上就保护数据。

## 8.2 在开发电脑上生成补丁

> **可能遇到：**`web-app/dist` 未构建、补丁脚本报错、版本/日期不对，或缺少 `.sha256`。
> [打开“生成升级补丁”AI 求助入口](./AI协作排错指南.md#ai-patch-build)

回到 `D:\fyt-src` 的 PowerShell：

```powershell
npm --prefix web-app run build
.\.venv\Scripts\python.exe scripts\build_linux_upgrade_patch.py
```

- 第一条：把最新网页编译出来（如果前端没改，也可以再跑一次，安全）。
- 第二条：生成补丁，文件名类似：

```text
dist\fyt-linux-upgrade-patch-v1.3.0-20260817.tar.gz
dist\fyt-linux-upgrade-patch-v1.3.0-20260817.tar.gz.sha256
```

文件名里的 `20260817` 表示 2026 年 8 月 17 日，由脚本按构建当天自动填写。同一天要发第二版，可加 `--revision r2` 区分；实际操作必须以本次生成的文件名为准。

> **为什么补丁生成前要先编译网页？**
> 补丁会把 `web-app/dist`（编译好的网页）打进包。不编译，脚本会报错“web-app/dist 尚未构建”。

## 8.3 上传补丁到服务器

> **可能遇到：**上传中断、文件传错目录，或补丁与 `.sha256` 不是同一次生成的配套文件。
> [打开“上传补丁”AI 求助入口](./AI协作排错指南.md#ai-patch-upload)

用 Workbench 上传（同 5.1），把 `.tar.gz` 和 `.tar.gz.sha256` 两个文件都传到 `/root`。

## 8.4 上传后先验包

> **可能遇到：**校验失败、文件名不匹配，或不确定能否跳过校验继续升级。
> [打开“补丁校验”AI 求助入口](./AI协作排错指南.md#ai-checksum)

```bash
cd /root
sha256sum -c fyt-linux-upgrade-patch-v1.3.0-20260817.tar.gz.sha256
```

输出 `...：确定` / `OK` 表示完整；否则重新上传。

> **为什么每次都验？**
> 一个字节的损坏都可能在升级中途引发问题。补丁脚本本身也会在应用前核对包内每个文件的哈希。

## 8.5 应用补丁

> **可能遇到：**SSH 中途断开、服务停下后没有恢复、脚本显示回滚，或不知道补丁是否仍在运行。
> [打开“应用补丁”AI 紧急求助入口](./AI协作排错指南.md#ai-patch-apply)

```bash
cd /root
tar -xzf fyt-linux-upgrade-patch-v1.3.0-20260817.tar.gz
cd fyt-linux-upgrade-patch-v1.3.0-20260817
sudo bash apply-upgrade.sh
```

`apply-upgrade.sh` 会自动按顺序做（每一步都有“为什么”）：

1. **校验补丁完整性**：确认包内文件与 `SHA256SUMS` 一致，防止篡改/损坏。
2. **校验服务器安装是否完整**：补丁只负责“升级”，不负责“首次安装”，发现缺东西立即停下。
3. **备份当前程序文件**到 `/var/backups/fyt-web/code-before-patch-时间.tar.gz`：可回滚。
4. **停止服务**：避免边运行边换文件，就像不能边开车边换轮胎。
5. **必要时更新 Python 依赖**：依赖清单没变就跳过，省时间。
6. **替换代码和前端**：只换 `web_server.py`、`web_backend/`、`core/`、`web-app/dist`、`requirements.txt`。
7. **语法检查 + 启动 + 健康检查**：确认新代码真的能服务。
8. **失败自动回滚**：任一步失败，旧程序自动恢复，并恢复升级前的启停状态。
9. **成功则保留旧程序备份**：升级前服务是停止状态的，验证后会恢复停止状态，尊重你原来的选择。

看到 `升级完成，业务数据目录未读取、未复制、未删除、未覆盖` 就成功。

## 8.6 升级后验收

> **可能遇到：**健康检查正常但页面仍旧、部分功能异常、浏览器白屏，或版本看起来没有变化。
> [打开“升级后验收”AI 求助入口](./AI协作排错指南.md#ai-upgrade-check)

```bash
sudo bash /opt/fyt/server/status.sh
curl http://127.0.0.1:8787/api/health
```

再用手机流量打开 `https://你的域名`，登录、点几个常用页面，确认一切正常。

## 8.7 如果用整包升级

> **可能遇到：**不确定备份、磁盘空间和旧服务是否准备好，或担心重新安装会重置账号。
> [打开“整包升级”AI 求助入口](./AI协作排错指南.md#ai-full-upgrade)

上传新版本 `fyt-server-linux-vX.Y.Z.zip`，解压后重新执行安装器即可：

```bash
cd /root
sha256sum -c fyt-server-linux-v1.4.0.zip.sha256
sudo unzip fyt-server-linux-v1.4.0.zip -d /opt/fyt
cd /opt/fyt/fyt-server-linux-v1.4.0
sudo bash install.sh
```

安装器会先备份数据（`/var/backups/fyt-web/pre-install-时间.tar.gz`）、备份旧程序、
切换新程序、健康检查；失败自动回滚。已有账号和密码不会被重置，`/var/lib/fyt-web` 不会被动。

# 第 9 段 · 日常运维手册

## 9.1 每日 / 每周 / 每月检查表

> **可能遇到：**看不懂 `active/failed`、磁盘百分比、日志中的偶发错误，或不知道是否需要立即处理。
> [把例行检查结果交给 AI 分级](./AI协作排错指南.md#ai-maintenance)

**每天花 2 分钟：**

```bash
sudo bash /opt/fyt/server/status.sh
sudo systemctl is-active fyt-web caddy
```

两条都正常即可。

**每周：**

1. 打开 `https://你的域名` 走一遍登录、上传小文件、下载，确认业务可用。
2. 看最近日志有无异常报错：`sudo bash /opt/fyt/server/logs.sh 200`。
3. 检查磁盘空间：`df -h`（`/` 的 Use% 别超过 80%）。

**每月：**

1. 手动做一次备份，并把备份文件下载到自己电脑或云盘。
2. 系统安全更新（选低峰期做）：

```bash
sudo apt-get update
sudo apt-get upgrade -y
sudo reboot
```

3. 检查阿里云账户里域名、服务器的**到期时间**，提前续费。

## 9.2 备份与恢复（重要！）

> **可能遇到：**备份失败、找不到备份文件、不会设置定时任务，或不确定恢复会覆盖什么。
> [先打开“备份与恢复”AI 安全入口](./AI协作排错指南.md#ai-backup)

### 手动备份

> **可能遇到：**脚本短暂停服后没有恢复、产物缺少 `.sha256`，或磁盘空间不足。
> [打开“手动备份”AI 求助入口](./AI协作排错指南.md#ai-backup)

```bash
sudo bash /opt/fyt/server/backup.sh
```

产物在 `/var/backups/fyt-web/fyt-data-时间戳.tar.gz`（带 `.sha256` 校验文件），默认保留最近 14 份。
脚本会短暂停服务以保证数据库一致性，几秒到几分钟后自动恢复。

> **为什么备份要短暂停服务？**
> 数据库正在写入时直接复制可能得到“半成品”文件。停一下再备，就像复印前先把文件合上。

### 自动每天备份（可选）

> **可能遇到：**不会保存 `crontab`、定时任务没有执行，或日志文件一直为空。
> [让 AI 帮我只检查定时备份](./AI协作排错指南.md#ai-backup)

```bash
sudo crontab -e
```

选择你熟悉的编辑器后，加入一行：

```cron
15 2 * * * /bin/bash /opt/fyt/server/backup.sh >> /var/backups/fyt-web/backup-cron.log 2>&1
```

含义：每天凌晨 2:15 自动备份，输出写到日志文件。

### 恢复备份（慎用）

> **高风险：**选错备份、解压到错误位置或在服务运行时恢复，都可能覆盖现有数据。
> [先打开“恢复备份”AI 安全检查，未确认前不要执行](./AI协作排错指南.md#ai-restore)

```bash
sudo systemctl stop fyt-web
sudo tar -xzf /var/backups/fyt-web/fyt-data-时间戳.tar.gz -C /
sudo systemctl start fyt-web
sudo bash /opt/fyt/server/status.sh
```

> **为什么恢复前必须停服务？**
> 运行时恢复数据会互相打架，可能造成数据库损坏。备份压缩包内保留了完整目录层级，解压回 `/` 即可还原到原位置。

## 9.3 管理员密码

> **可能遇到：**初始密码没保存、重置命令报错、改密后仍无法登录，或不知道 Windows/Linux 应走哪套步骤。
> [打开“管理员密码”AI 求助入口（不要发送密码）](./AI协作排错指南.md#ai-password)

- **记住初始密码**：Linux 安装器生成/接受的初始密码只在首次建库时有效，健康检查成功后自动从配置删除。请立即记在密码管理器中。
- **日常改密**：登录系统后在“账号安全”里修改。
- **Linux 忘记密码**（紧急，需谨慎，密码不会显示在屏幕上）：

```bash
sudo systemctl stop fyt-web
cd /opt/fyt/server
sudo -u fyt-web env FYT_WEB_DATA=/var/lib/fyt-web .venv/bin/python - <<'PY'
import getpass, os, web_server
p = getpass.getpass("请输入新管理员密码（至少10位，含字母和数字）: ")
if not (10 <= len(p) <= 128 and any(c.isalpha() for c in p) and any(c.isdigit() for c in p)):
    raise SystemExit("密码不符合要求")
salt, digest = web_server.hash_password(p)
web_server.init_db()
conn = web_server.db()
conn.execute("UPDATE users SET salt = ?, password_hash = ? WHERE username = ?", (salt, digest, "admin"))
conn.commit()
conn.close()
print("管理员密码已更新")
PY
sudo systemctl start fyt-web
```

- **Windows 包忘记密码**：停止服务后，在包目录打开 PowerShell，执行 `.\重置管理员密码.ps1`（被策略阻止时先执行 `Set-ExecutionPolicy -Scope Process Bypass -Force`）；旧版包请重新打包后再用该工具。

## 9.4 常见故障排查表

> **可能遇到：**现象不在表中、同时出现多个错误，不知道哪个才是根因。
> [让 AI 按浏览器→Cloudflare→Caddy→应用→数据逐层定位](./AI协作排错指南.md#ai-diagnose)

| 现象 | 先看什么 | 常见原因和动作 |
| --- | --- | --- |
| `curl` / `unzip` / `nano: command not found` | `cat /etc/os-release` | 基础依赖未安装；回到 2.5 节，只执行匹配当前系统的一组命令 |
| 安装卡在 Python 依赖 | 终端最后 30 行；出方向 53/443 | 网络慢或 PyPI 连接失败；先等候，再用 5.4 节的 `PIP_INDEX_URL` 镜像命令重试 |
| `No module named venv` | `python3 --version` | 对应 Python 的 venv 组件缺失；Ubuntu 安装 `python3-venv`，其他系统重新安装对应版本 Python 包 |
| `caddy: command not found` / `Unit caddy.service not found` | 第 6.2、6.3 节安装输出 | Caddy 软件源或安装包未成功；不要继续写证书和配置 |
| Caddy 日志出现 `address already in use` | `sudo ss -lntp`，查找 `:80` 和 `:443` | 80/443 已被 Nginx、Apache 或旧 Caddy 占用；确认旧服务用途后再决定停用，不能让两个程序抢同一端口 |
| Caddy 日志出现 `permission denied` 读取 `.key` | `sudo ls -l /etc/caddy/certs/` | 私钥权限或属组错误；应为 `-rw-r----- root caddy`，按 6.4 节重新设置 |
| 公网打不开 | `curl http://127.0.0.1:8787/api/health` | 无 `ok` → `sudo bash /opt/fyt/server/logs.sh 100` 查应用 |
| 公网打不开，但本机正常 | Cloudflare DNS A 记录、橙色云和阿里云安全组 | 公网 IP 填错；记录仍是灰色云；80/443 没有放行 Cloudflare IP 段；存在错误 AAAA 记录 |
| Cloudflare 显示 522 | `sudo systemctl status caddy`；安全组 80/443 | Cloudflare 无法连接源站；Caddy 未监听、服务未启动，或安全组遗漏了 Cloudflare 地址段 |
| Cloudflare 显示 525/526 | `sudo journalctl -u caddy -n 50 --no-pager`；核对证书域名和有效期 | TLS 握手失败、证书与域名不匹配、私钥与证书不配套，或 `Full (strict)` 无法验证源站证书 |
| 打开是 404 / 白页 | 核对 `/etc/caddy/Caddyfile` 中的域名和 `reverse_proxy` | 域名写错、Caddy 配置未重载，或请求落到其他站点配置 |
| 打开是 502 Bad Gateway | `sudo systemctl status fyt-web` | 后端没运行或端口不是 8787；查 `/etc/fyt-web/fyt-web.env` |
| 登录页正常但登录报错 | 账号密码 | 初始密码是否记对；用 9.3 重置流程 |
| 升级后异常 | `sudo bash /opt/fyt/server/logs.sh 100` | 补丁脚本通常已自动回滚；整包安装失败版本会保留在 `/opt/fyt/server.failed-时间`，补丁备份在 `/var/backups/fyt-web/code-before-patch-*` |
| SSH 连不上 | 阿里云 Workbench 能否连 | 22 端口来源 IP 规则；家庭宽带 IP 变了，更新安全组 |
| 下载/更新失败 | 出方向安全组 | 推荐方案检查 80/443/53；Tunnel 备选方案再检查 7844；临时放通全部出方向只用于短时定位 |
| 域名实名未过 | 阿里云域名列表 | 提交材料不清晰；重新提交 |
| Cloudflare 站点一直 Pending | 阿里云 NS 设置 | 两个 NS 是否填对；等待 24 小时再查 |

## 9.5 安全习惯（每一条都很便宜，但出事很贵）

> **可能遇到：**怀疑密码、私钥、Token 或服务器账号泄露，不知道先撤销什么、是否应暂停公网。
> [打开“疑似泄露”AI 止损入口](./AI协作排错指南.md#ai-security)

1. **绝不把密码、token、私钥写进文档、聊天记录、Git 仓库。**
2. 服务器 22 端口只对自己的 IP 开放；不用时关闭。
3. Cloudflare、阿里云账号都开启两步验证。
4. 定期改管理员密码；离职员工账号及时停用。
5. 服务器系统和 Caddy 定期升级；只有启用 Tunnel 备选方案时才需要维护 `cloudflared`。
6. 备份文件至少留一份在服务器之外（下载到自己电脑/云盘）。
7. 不要在群里贴 `https://你的域名` 的完整后台截图，截图可能带敏感数据。

## 附录 A · Cloudflare Tunnel 备选方案

> **可能遇到：**授权失败、Tunnel 显示 degraded、QUIC 反复超时，或固定 Tunnel 和传统 A 记录冲突。
> [打开“Cloudflare Tunnel”AI 求助入口](./AI协作排错指南.md#ai-tunnel)

> 适用：服务器没有稳定公网 IP、不能开放入站 80/443，或者网络策略明确要求服务器只能主动向外连接。
> 正常情况下请使用正文的传统方案。不要因为 Tunnel 看起来“少开端口”就忽略它的授权凭据、后台服务和额外排错成本。

### A.1 安全组差异

> **可能遇到：**不知道 7844 应放在入方向还是出方向，或传统规则是否需要保留。
> [让 AI 按 Tunnel 备选链路核对规则](./AI协作排错指南.md#ai-tunnel)

- 入方向不需要开放 80/443，8787 仍然不开放。
- 出方向在 80/443/53 之外，再允许 UDP 7844 和 TCP 7844 到 `0.0.0.0/0`。
- Web 服务继续监听 `127.0.0.1:8787`。

### A.2 使用固定命名 Tunnel

> **可能遇到：**浏览器授权无法完成、服务不是 `active`，或日志不断重连。
> [打开“固定 Tunnel”AI 求助入口](./AI协作排错指南.md#ai-tunnel)

Linux 包在 `/opt/fyt/server` 中附带：

- `cloudflared.sh`：临时 Quick Tunnel，只用于短时测试，地址可能变化。
- `cloudflared-named.sh`：固定命名 Tunnel，可绑定自己的域名并安装为 systemd 服务。

正式备选入口使用固定命名 Tunnel：

```bash
cd /opt/fyt/server
sudo bash cloudflared-named.sh
```

脚本会要求浏览器授权 Cloudflare 账号、输入 Tunnel 名称和公网域名，并询问是否安装为系统服务。选择安装服务后，执行：

```bash
sudo systemctl status cloudflared --no-pager
sudo journalctl -u cloudflared -n 50 --no-pager
```

状态应为 `active (running)`，日志中不应持续出现连接超时或反复重连。

### A.3 避免与传统 A 记录冲突

> **可能遇到：**同一域名同时存在 A 和 CNAME、不知道应先测试还是直接切换正式域名。
> [让 AI 帮我检查 DNS 冲突，但先不要删除记录](./AI协作排错指南.md#ai-tunnel)

同一个域名不能同时保留传统 A 记录和 Tunnel 创建的 CNAME。建议先用单独的测试子域名（例如 `fyt-tunnel.example.com`）验证 Tunnel；
确认可用并决定正式切换后，再删除原 `fyt` A 记录并让脚本为正式域名创建 CNAME。切换完成后，关闭不再需要的 80/443 入方向规则。

若只是临时诊断，不要修改正式域名：

```bash
cd /opt/fyt/server
sudo bash cloudflared.sh --daemon
sudo bash cloudflared.sh status
sudo bash cloudflared.sh stop
```

Quick Tunnel 的 `trycloudflare.com` 地址不固定，不能作为正式业务入口。
