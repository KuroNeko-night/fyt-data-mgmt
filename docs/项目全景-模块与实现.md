# 项目全景：模块与实现

> 最近核对：v1.3.0（2026-08-11）。本文只记录当前代码、运行入口和交付方式。

## 一、总体架构

```text
core/              Python 纯业务逻辑、主数据、路径、缓存、任务历史和桥接
tauri-app/         React 19.2 + Vite 8.1 + Tauri 2.11 桌面端
web-app/           React 19.2 + Vite 8.1 Web 前端
web_server.py      Web 兼容启动入口、运行配置与依赖组合根
web_backend/       HTTP Handler、路由、任务运行器、数据库和领域 API 服务
web_control_gui.py Tkinter/ttk Web 服务与 Cloudflare Tunnel 控制台
design-system/     Web 与 Tauri 共用设计令牌
assets/            品牌资源与已投入运行的生成美术资源
packaging/         Tauri sidecar、Windows Web 包、Linux 部署和升级脚本
scripts/           构建、发布、资源同步、部署打包和质量检查
tests/             unittest 合成数据回归
docs/              当前实现与使用说明
```

双端业务链路分别为：

```text
Tauri React -> Rust 白名单命令 -> core.tauri_bridge -> core/*
Web React   -> 同源 /api       -> web_server.py + web_backend -> core.tauri_bridge -> core/*
```

React 负责交互和展示；Rust 与 Web 服务负责动作白名单、进程管理、权限、用户隔离和事件转发；业务算法只在 `core/` 维护。

当前 Web 提供 19 个业务入口，Tauri 提供 27 个导航页面，`core.tauri_bridge` 注册 63 个白名单动作。采购差异清单嵌入采购计划流程，票货匹配嵌入财务流程，不要求为每个动作增加独立导航页。

## 二、共享基建与单一事实来源

### 版本、路径与配置

- `core/version.py` 保存应用名称、应用 ID、发布者、更新地址、`VERSION`、`VERSION_TUPLE` 和 `BUILD_DATE`。当前版本为 `1.3.0`。
- 发布版本需要同步两个 `package.json` 及锁文件、`tauri-app/src-tauri/Cargo.toml`、`Cargo.lock` 和 `tauri.conf.json`；`scripts/release.mjs` 负责自动核对与同步。
- `core.paths.config_path()` 是配置路径入口。桌面端默认使用用户文档目录下的应用数据目录；Web 任务通过 `FYT_CONFIG_PATH` 指向账号隔离的运行目录。
- `core.paths.resolve_output_dir()` 统一处理固定目录、源文件旁目录和自定义目录；功能中文目录由 `FEATURE_DIRS` 管理。
- Web 数据根由 `FYT_WEB_DATA` 指定，未设置时使用项目下的 `web-data`。账号数据库、上传、任务结果、回收站、备份、日志和私密配置均位于该数据根，不属于源码。

### 并发、安全写入与缓存

- `core/storage_lock.py` 为 JSON 索引提供跨进程文件锁，并在 Windows 文件锁外增加进程内 `RLock`。
- 配置、索引和主数据采用“文件锁 + 临时文件 + 原子替换”写入，避免并发中断产生半文件。
- `core/task_history.py` 使用 SQLite 保存桌面端任务状态、耗时、输出目录、说明和 `request_id`；取消与完成更新遵循状态条件，不覆盖已取消任务。
- `core/incremental_cache.py` 按输入内容、参数和相关主数据指纹生成缓存键，命中前验证输出存在。Web 为每个账号设置独立缓存路径。
- `core/common_core.py` 是公共基础设施的稳定兼容入口；纯值解析位于 `core/common_parsing.py`，Excel 安全读取、公式缓存检查、透视缓存和外部链接跳过位于 `core/common_workbook.py`。业务模块继续从 `common_core` 导入原名称，解析规则与工作簿内部兼容处理可以分别维护；`load_data_only_stream()` 用于不需要样式和随机写入的大表顺序读取。只读业务不恢复工作簿外部链接，避免少量业务数据因数百个历史链接产生分钟级解析和高内存占用。
- `core/header_detect.py` 与 `core/shape_detect.py` 负责表头、列角色和表格形态识别；形态推断只作为自动识别和人工确认的辅助依据。兜底识别依次完成数据区定位、列画像采样、未占用列评分、角色指派和必填角色校验；日志回调失败不影响只读识别结果。

### 主数据、映射、模板与文件分类

- `core/material_catalog.py` 是正式主数据库，维护供应商名称到代码、材料编号到名称/规格/单位/供应商的对应关系。业务运行只用正式主数据补空，不覆盖源表已有内容。管理员关系合并按“输入规范化、乐观并发冲突检测、快照备份、分类应用、单次原子提交”分层，关系读取与写入共享同一类型映射。
- `core/master_data_import_core.py` 负责管理员上传表格后的关系学习、来源定位、重复文件识别、冲突分析、人工治理、确认和合并。存在冲突的批次不能直接写入正式库。
- `core/mapping_store.py` 按表头结构指纹保存字段映射确认结果；`core/template_store.py` 管理模板族、版本、结构差异和显式迁移规则。
- `core/library.py` 是数据库文件分类的对外事实源，维护 `CATEGORIES`、`CATEGORY_TITLES` 和稳定公开操作；`core/library_classification.py` 按注册表维护各业务评分器，`core/library_scan.py` 负责 xlsx/xlsm/xls 的有限表头扫描，`core/library_storage.py` 负责归档、删除和人工重分类的文件事务步骤。启动时会校验类别顺序与评分注册表完全一致，新增业务分类不会因漏改规则而静默落入未识别。

### 桥接与结构化业务结果

- `core/tauri_bridge.py` 从 stdin 接受单次 JSON 请求，从 stdout 返回结果，从 stderr 输出带 `request_id` 的日志和进度事件；所有动作必须进入 `_ACTIONS` 白名单。载荷校验、长任务包装和全部动作处理器已拆到 `core/tauri_bridge_actions.py`，入口文件只保留协议、分派和 main。
- 桥接统一校验路径、必填列表、目录参数和 JSON 可序列化结构，并把标准流设为 UTF-8。
- `core/business_result_core.py` 是 15 类业务结果投影的兼容入口；公共规范化位于 `business_result_common.py`，到料与考勤位于 `business_result_daily.py`，采购运营位于 `business_result_operations.py`，财务与通用比对位于 `business_result_finance.py`。最终统一生成业务标题、结论、语义指标、可信度、本次采用设置、明细表和核对提示。送货计划投影把供应商与参考计划覆盖评分、待补物料明细和最终协议组装分开维护，评分口径与公开字段保持稳定。
- 已注册投影包括：考勤填报、考勤月度归档、工时对账、到料明细、采购汇总、采购对账、发运评审对比、送货计划、供应商批次表、采购计划导入、采购差异清单、对账单制作、发票统计、票货匹配和表格比对。
- 可信度采用 0～100 分、等级、评分口径和逐项核查依据；只评价识别、字段完整性、匹配覆盖和处理依据，不把真实业务差异当成程序低可信。
- 到料投影完整保留各批次未到物料、需求数、已收数和缺口数；一般明细默认限制预览行数并标明总数，正式报告仍可下载。
- 投影生成失败只增加处理提示，不改变已经成功的核心任务结果。

### 双端设计系统

- `design-system/tokens.json` 是颜色、排版、间距、圆角、控件高度、布局、阴影、动效、图标和状态映射的单一事实来源。
- `scripts/sync-design-tokens.mjs` 生成 Web/Tauri 的令牌样式和状态映射；生成文件不手工维护。
- `assets/generated/manifest.json` 记录当前投入运行的 A01～A07 美术资源；`scripts/sync-art-assets.mjs` 负责同步到双端静态目录，`scripts/optimize-art-assets.py` 负责透明边缘、裁切和压缩等本地后处理。
- 双端共用 `Button`、`IconButton`、`Surface`、`PageHeader`、`StatusBadge`、`Notice`、`FormField`、`SegmentedControl`、`DataTable`、`TaskRow`、`FileRow`、`EmptyState`、`Skeleton`、`Dialog` 和 `Drawer` 等语义组件。
- 页面背景使用蓝、青和淡粉光晕的缓慢流动渐变；业务卡片使用半透明玻璃表面、蓝图纹理、内高光和分层阴影。所有动效尊重 `prefers-reduced-motion`。
- 滚动容器隐藏可见滚动条，但保留滚轮、触控板、触摸和键盘滚动；侧栏、顶栏和移动端底栏不随内容区滚动。

## 三、业务模块

### 人事与考勤

- `attendance_core.py`：保留考勤任务入口和工作簿写入；`attendance_source.py` 独立维护人工列映射优先级、源表头识别、短行安全读取和多文件重复打卡合并。写入阶段继续按姓名与完整日期匹配，并计算班次、实际工时、加班和异常；支持白班标准工时、加班开关、时间进退位、重复记录策略、合理工时上限、跨零点夜班和额外假休标记等参数。
- `attendance_archive_core.py`：自动识别姓名、日期、工时、加班和异常列，把多份考勤填报表汇总为月度统计与每日明细。入口依次执行全量文件校验、记录聚合、输出目录解析和双页工作簿保存；人员汇总、主体月份、表头样式和明细排序分别维护，历史返回字段保持稳定。
- `reconcile_core.py`：聚合来源工时并与目标表、劳务表逐日和总计对账，输出差异汇总、异常明细和可信度；支持工时差异容差与重复记录策略。主流程按“来源读取、总表填写、劳务合并、比较、评估、汇总”分阶段编排，姓名/日期/合计列识别、名单差异和逐日差异均为独立可测试单元；任一后续阶段失败都会释放可写工作簿与公式缓存副本。来源与劳务识别层已拆到 `reconcile_sources.py`，总表布局识别与填表已拆到 `reconcile_zong.py`；可信度扣分规则、异常汇总工作簿和可信度工作表集中在 `reconcile_reporting.py`，业务识别不再混入 Excel 报告样式。

### 到料、销售与采购

- `arrival_core.py`：扫描送货计划表头下具有物料编码的全部数据行，自动统计主料总类数，不受 Excel 筛选或隐藏状态影响；“剩余未收数”为非零数字的物料自动列为未到料。表头文字和成品报表共用同一字段归类器，送货计划读取按“列解析、逐行统计、提示输出”分层；成品表按“锚点、指标、明细、批次”分层解析。材料或供应商为空时从正式主数据补全；生成每日到料表并返回批次级缺料明细。`analyze_finished_report()` 可直接读取人工上传的成品每日到料表。
- `pivot_core.py`：采购汇总业务入口，负责第二阶段应用、静态主表/清洗子表输出、来源最终采购数自检、缓存命中和正式运行编排，并保留拆分模块的公开名称重导出。结构识别、分类、清洗与第一阶段复核计划位于 `pivot_analysis.py`；规格/单位归并与静态聚合位于 `pivot_clustering.py`；可信度扣分与兼容文本报告位于 `pivot_reporting.py`。横向子表按材料编号锚点和下一个锚点边界直接提取，避免生成中间并排表；第二阶段按“收集页签选择、记录来源数量基准、恢复人工保留行、规范化、单位归并、物料号聚合、来源与最终表勾稽、静态落盘、组装审计结果”编排。输出只包含采购汇总主表和清洗数据子表，不再维护原生透视缓存、OOXML 注入或重复汇总列；若来源汇总与最终表汇总不一致，结果会进入严重风险并在双端结构化结果中明确展示差异。
- `purchase_core.py`：对双方采购数据进行主数据补全、候选匹配和最小费用最大流配对，输出上色副本与汇报单，避免按行贪心导致漏配。来源页签选择、业务行解析、残量网络构造与增广、未匹配诊断、数量疑点、原表补空上色和输出编排均为独立单元；Excel 上色与汇报单渲染已拆到 `purchase_reporting.py`，运行日志保持先说明主数据补全、再说明双方有效行的既有顺序。
- `shipping_review_core.py`：读取包装日计划，严格排除 `BOX状态=已作废` 的记录，按物料号与物料描述形成包装透视；评审侧默认读取工作簿保存时的活动页签，也允许人工覆盖。双方同一物料的拆分行均先按物料号累加再比较，避免多供应商或多 BOX 记录覆盖。输出对比总表、异常明细、包装透视和过滤审计四页签报告，并把数量差异、名称缺失/不一致和单侧物料作为结构化结果同步到 Web 与 Tauri。
- `delivery_core.py`：合并物料清单与供应商资料，识别子表和字段后生成送货计划；缺少独立供应商明细时可由正式主数据兜底。输入读取分为页签选择、可选字段读取、汇总行过滤和业务行投影；自动模式仅在首表无法识别时顺序寻找后续页签，显式页签仍严格按用户选择处理。参考计划按“定位首个明细页、投影 CASE/托数/班组、按编码保留首条有效记录”读取，空补充行不会阻止后续同编码有效记录。
- `supplier_batch_core.py`：扫描批次与供应商，按当前数据、历史供应商明细和正式主数据依次补空；统一排除材料名称中的“原厂”内容；生成前要求为每个批次填写交付日期并选择供应商。扫描流程分为输入校验、历史映射、当前批次读取、有效记录校验、供应商归属和复核摘要；正式执行再校验本次供应商选择与批次日期，随后按供应商生成文件并统一组装日志和返回结果。
- `purchase_plan_core.py`：读取采购计划模板和一份或多份辅料清单，补全材料及供应商代码，生成批次采购计划；同时提供采购差异清单。批次行解析、模板清理、模板写入、输出规划、临时转换、原子提交、失败回滚和主数据学习均为独立阶段；实收差异按“单批次读取、业务行筛选、报告写入”分层。多批次任一阶段失败都不会留下部分正式结果，也不会提前污染主数据。
- `reconcile_statement_core.py`：扫描采购清单中的横向或纵向批次块，排除指定标注色行，补全主数据和供应商后按所选批次生成对账单。标题边界、活动块状态、材料行解析、单文件预览、供应商推断、选中数据归并和文件输出分别由小函数承担，扫描与生成阶段不再共享嵌套状态机。

### 财务、批次与报表

- `invoice_core.py`：递归扫描增值税专用发票 PDF，逐张确认后按月生成发票台账。
- `invoice_match_core.py`：按供应商匹配发票台账与采购明细，标记无票采购和有发票无采购；输入校验、表头单行角色识别、完整角色判断、两侧读取汇总、集合匹配和报告写入分别维护，报告保存失败时仍会释放工作簿句柄。
- `report_center_core.py`：把任务记录汇总为带统计与明细工作表的业务报表，支持近 7 天、近 30 天、本月和全部范围。

### 日清、生产与现场管理

- `daily_safety_check_core.py`：读取安全检查表内的检查日期、类别、项目、标准、结果、问题、整改、责任人和内嵌图片，生成当日安全检查结构化数据。文件打开、页签选择、日期读取、明细投影、结果分类、图片关联和摘要组装分别维护；“不合格”始终优先于“合格”判定。
- `daily_production_plan_core.py`：识别生产计划矩阵、班组/批次重点、月度正式订单台账、缺件/危包子项、零星订单和发运信息；横向矩阵与传统逐行表分别转换成统一班次记录，再汇总已填报计划、未填报计划、完成率和重点提示。正式订单与零星订单都按“创建主对象、合并跨行字段与子项、统一计算状态”处理；零星订单的运输信息、唯一日期、备注、托盘明细和最终数量分别聚合。洞察总装把单页计划解析、生产实绩辅助数量和空协议构造拆开，生产实绩只能补充已有计划，不会单独伪造完成率。
- `workshop_issue_core.py`：校验 JPG、PNG、WebP 现场图片，修正手机 EXIF 方向并限制解压像素；严格按主料异常、辅料异常、包装异常、海外历史记录、防错异常五类模板校验字段和导出工作表。Web 新建草稿与编辑入口共用同一字段白名单、必填项、长度限制和负责人/严重度派生规则；旧客户端未显式选择分类时仍可先建立草稿，再在发布前完成校验。主料、辅料、包装和海外问题需要图片，防错异常不要求图片。日期范围导出最长 366 天，多张图片按两列嵌入；Excel 输出把样式、分组表头、普通表头、正文图片和工作表级打印配置分开维护，保持规范模板版式。
- `daily_report_core.py`：保留 `build_snapshot()` 和 `run()` 两个稳定入口。`daily_report_snapshot.py` 只负责日期校验和快照总装；到料、现场问题、考勤、月度订单台账和值规范化分别位于 `daily_report_arrival.py`、`daily_report_workshop.py`、`daily_report_attendance.py`、`daily_report_production.py` 和 `daily_report_values.py`。`daily_report_excel.py` 使用同一快照生成分段 Excel，页面与导出口径不会分叉。

### 主数据库学习

- 管理员可上传 xlsx、xlsm 或 xls。系统识别供应商名称→编码以及材料编号→名称/规格/单位/供应商五类关系，并保存来源工作表与行号。

## 四、工具模块

- `library.py`：文件自动分类、归档、索引、重新分类、删除与回滚边界；格式扫描和文件事务分别下沉到 `library_scan.py` 与 `library_storage.py`。导入、删除和人工重分类按“准备备份、提交文件、原子保存索引、失败回滚”执行，重分类失败还会恢复当前内存索引条目。
- `currency_core.py`：金额转中文大写，拒绝 NaN 和 Infinity。
- `text_core.py`：去重、排序、清理、大小写转换、编号与邮箱/电话/网址提取。
- `rename_core.py`：批量重命名预览、冲突检测、执行与撤销。
- `pdf_core.py`：PDF 合并、拆分、提取和删页；先读入内存，避免 Windows 文件锁影响源文件。
- `excel_tools_core.py`：Excel/CSV 合并、拆分、转换和纵向拼表；纵向合并分别维护表头键规范化、列重排计划和单行宽度对齐，拒绝结构缺失，并在验证或保存失败时关闭输出工作簿。
- `compare_core.py`：按关键列比较两张表，使用 Decimal 处理数值并保留前导零编码语义；比较列验证、完全一致行消去和同键剩余行的最少差异配对分别维护，重复键会按内容相似度逐条配对并提示人工核对。
- `preview_core.py`：只读工作表名称和前若干行，为双端文件预览提供轻量数据。
- `updater.py`：校验 HTTPS、文件长度、扩展名和 SHA-256，使用 `.part` 下载并在通过校验后原子替换；响应打开、分块写入、半包清理和验证提交相互独立，任何连接、读取、写入或校验失败都不会把半包暴露为安装器。

## 六、Web 端

### 认证、角色与权限

- `web_server.py` 只保留兼容启动、运行配置、依赖工厂和少量历史公开包装；HTTP 协议与端点绑定位于 `web_backend/http/handler.py`，根入口不再保存近百个重复领域委托方法。`web_backend.server_runtime` 使用标准库 `ThreadingHTTPServer` 创建服务，并调度存储清理、自动备份、周报和月报。`web_server.py --reset-admin-password` 是冻结部署包的管理员密码重置入口，新密码只经环境变量传入，不进入命令行参数或日志。SQLite 保存用户、会话、审核、上传、任务、现场问题、日清、消息和管理记录。
- `web_backend/` 是 Web 服务端实际实现边界，已包含运行配置、服务生命周期、数据库连接与初始化、JSON 兼容转换、公开结构整理、HTTP Handler 与路由，以及认证、账号、消息、任务、文件库、现场问题、日清、主数据、存储维护、管理数据、备份、回收站、报表中心、工作台聚合和临时上传服务。HTTP 方法通过 `http/routes.py` 分发，`http/handler.py` 负责协议和按领域声明式端点绑定；JSON 与文件响应、异常转换、会话上下文、路径编号、权限判断和静态资源分别由 `responses.py`、`context.py`、`path_params.py` 和 `static_files.py` 处理。Core 子进程生命周期、Web 特殊动作编排、结果文件投影和后台任务状态机分别位于 `tasks/bridge.py`、`tasks/actions.py`、`tasks/results.py` 和 `tasks/runner.py`。`database/schema.py` 声明当前完整表结构和索引，`database/migrations.py` 按数据域执行幂等字段升级与历史迁移，`database/initializer.py` 只负责编排同一事务内的执行顺序。`presenters.py` 统一生成账号、日清、文件库和现场问题的前端公开结构，其中安全检查图片 URL、文件分类清洗、公开身份和逐记录权限均由独立小函数生成，不把服务器路径下发给浏览器。
- 密码使用随机盐与 PBKDF2-HMAC-SHA256。密码至少 10 位且同时包含字母和数字；登录失败按账号与来源地址计数，15 分钟内连续失败 5 次后锁定 15 分钟。
- 会话活动时间默认最多每 60 秒写回一次，可通过 `FYT_SESSION_TOUCH_INTERVAL_SECONDS` 调整，减少高频页面请求对 SQLite 的写锁竞争。
- 注册账号必须经管理员审核。首次建库必须通过 `FYT_ADMIN_PASSWORD` 或控制台安全输入提供管理员密码；未提供时服务拒绝初始化。登录页不显示管理员账号或密码。
- 新会话使用 `HttpOnly`、`SameSite=Strict` Cookie；账号可查看并移除设备会话，修改或重置密码会撤销相应会话。

### 任务、输出与数据安全

- Web 业务目录以 `web_server.py` 的 `FEATURES` 为准；业务动作受 `WEB_ACTIONS` 和 `REVIEW_ACTIONS` 限制，表单协议以 `FeatureWorkspace.SPECS` 为准。
- 复核类任务先执行只读分析，返回确认计划；用户选择后在同一任务中继续最终执行。供应商批次、工时对账、采购汇总、发票和表格比对使用该协议。
- 业务结果和字段映射中的来源路径先统一 Windows 与 POSIX 分隔符，再提取文件名；Linux 服务可以安全展示和复用由 Windows 客户端产生的历史任务与映射配置。
- 到料明细在正式处理前先扫描每份送货计划，双端逐批展示批次号、自动主料总类数、未到料类数和备注；自动值预填后仍允许人工覆盖主料总类数，正式任务以人工复核值为准。
- 上传、配置、缓存、任务历史、输出和运行 HOME 按用户 ID 隔离。上传句柄、任务参数、下载、预览和导出均校验所属账号及允许目录。
- 普通业务上传由 `web_backend.services.uploads` 统一保存和解析；文件流中断或数据库记录失败时清理未完成文件，上传句柄、上传批次和绝对路径均必须落在当前账号上传目录内。
- 日清维护的原导入路径 `services/daily_management.py` 是兼容门面；人员、班组、班次和考勤位于 `daily_people.py`，事项与待办位于 `daily_briefs.py`，生产计划、成品到料、安全检查与导出位于 `daily_files.py`，共享依赖契约位于 `daily_management_types.py`。考勤请求先在事务外规范化并批量校验人员与班次；班组校验把名称、排序、启用状态、可选班次快照和单班次规则分开处理，未提交班次与显式空列表保持不同语义。日清事项按共享字段读取、类别/状态校验、类别字段清理和日期/长度校验分层。成品资料上传按“请求参数校验、隔离目录落盘、Core 解析、表内日期核对、数据库与审计同事务提交”的固定顺序执行；任一阶段失败会删除尚未建立有效索引的上传目录。文件资料复用流式接收和可补偿回收站事务，数据库失败会把目录移回原位。
- 所有业务下载统一使用流式文件响应，响应层集中设置内容类型、文件长度、UTF-8 下载名和缓存规则；现场图片保持短时私有缓存，业务结果、报表和备份禁止缓存。Web 入口 HTML 使用 `no-store, must-revalidate, no-transform`，既避免部署后复用旧入口，也禁止 Cloudflare 等中间代理改写页面并注入不属于项目的检测脚本。
- 每次成功任务保存结果版本；任务中心支持搜索、取消、重试、在线预览、下载和限时匿名分享。管理员可把任务指派给指定账号。
- CSV、XLSX、XLSM、TXT 和 JSON 支持限行在线预览；PDF 通过浏览器打开或下载。结构化结果与可信度直接显示在页面中，正式报告仍作为文件提供。
- 默认只保留每个账号最近 20 个包含结果文件的已完成任务，超出部分进入回收站；待确认任务不自动归档。回收站默认保留 30 天，未发布现场问题草稿保留 24 小时。
- 普通文件上限 200 MB，主数据导入上限 50 MB，JSON 请求体上限 4 MB；数据库账号默认配额 2 GB。
- 服务每 6 小时执行存储维护；每天创建自动备份并滚动保留 7 份，手动备份不参与自动清理。备份清单记录文件大小和 SHA-256，校验器分别验证清单版本、目录白名单、重复路径、逐文件流式哈希和 ZIP/清单一一对应；恢复前创建安全备份，恢复后清除全部会话。

### 现场问题

- 页面采用移动端优先布局，支持调用后置摄像头、多选相册、本地预览、图片移除、上传进度、日期切换、图片大图和 Excel 导出。

### Web 前端与控制台

- 静态入口页和前端路由回退使用 `no-store`，防止部署新版本后旧 HTML 引用失效哈希；Vite `assets/` 哈希资源使用一年不可变缓存，其他固定资源缓存七天。
- Web 外壳由 `WebShell.tsx`、`AppSidebar.tsx`、`AppTopbar.tsx`、`MobileNavigation.tsx` 和 `MoreDrawer.tsx` 组成；桌面使用侧栏，平板使用图标栏，移动端使用固定底部导航和更多抽屉。
- Web 路由舞台 `fyt-route-stage` 只允许透明度入场动画，不能添加 `transform`、`filter`、`perspective` 或绘制隔离；舞台位于主滚动容器内，而主数据复核、文件编辑和现场问题编辑等弹窗使用 `position: fixed`，必须始终相对浏览器视口定位，不能相对已滚动的业务内容定位。
- 工作台由 `DispatchBoard.tsx` 提供，展示待确认、处理中、排队、异常任务、需要处理事项、快速开始、最近任务和近七日创建趋势。
- `FeatureWorkspace.tsx` 统一文件上传、拖放、参数、预检、常用模板、两阶段确认、取消、结果、在线预览和历史版本；业务结果在主工作区全宽展示。
- Web 请求层 `api.ts` 统一封装同源 `/api` 请求；接口类型契约已拆到 `web-app/src/api/types.ts`，会话令牌访问器拆到 `web-app/src/api/client.ts`，页面继续从 `api.ts` 导入而不感知内部拆分。
- `BusinessResultView.tsx` 展示全部已注册结构化结果与可信度；正式输出仍可下载。
- 页面使用亮暗主题、结构化骨架、错误边界、断网提示和有限次数 GET 重试；登录页装饰层不接收鼠标事件，适配移动端竖屏输入。
- 客户界面不展示动作 key、任务 ID、绝对路径、运行时、桥接、Python、调试口径和实现过程。
- `web_control_gui.py` 使用标准库 Tkinter/ttk 管理 Web 服务、临时 Tunnel 和固定命名 Tunnel；使用 `pythonw.exe`、`CREATE_NO_WINDOW` 与冻结程序入口隐藏子进程命令窗口。PID 文件校验与进程终止等非 Tk 逻辑已拆到 `web_control_gui_process.py`。
- GUI 与 PowerShell 脚本共用数据根下的 PID、日志和公网地址文件，只停止经过 PID 校验的本部署实例。固定 Tunnel 令牌使用 Windows DPAPI 加密保存，不回显、不进入命令行或日志。

## 八、打包与部署

### Tauri 桌面端

- `npm --prefix tauri-app run tauri:build` 调用 `scripts/build-tauri.ps1`，先核对多端版本并构建 `FYTCoreBridge.exe`，再生成 MSI 和 NSIS 安装包。
- `packaging/tauri_bridge.spec` 收集 `core` 子模块并排除 Tkinter、科学计算和开发依赖。

### 三类交付包

`scripts/build_deploy.py` 输出到 `dist/`：

- `峰运通数据管理系统_源码_v<版本>.zip`：纯净源码、测试、设计资源、当前文档，以及 README 引用的 Web 启停、图形控制台、隧道和管理员密码维护脚本；排除虚拟环境、依赖目录、构建产物、运行数据、日志、缓存、可执行文件、安装包、数据库、证书和私钥。
- `峰运通服务端_windows_v<版本>.zip`：`web_server.exe`、`bridge_worker.exe`、Tkinter 服务控制台、`web-app/dist`、启动/停止与密码重置脚本、`cloudflared.exe` 和使用说明。三个冻结程序保留各自 `_internal` 目录。
- `fyt-server-linux-v<版本>.zip`：ASCII 文件名与包内根目录，包含服务端源码、`core/`、静态前端、精简依赖和 `packaging/linux/` 管理脚本，并生成同名 `.sha256`。

### Docker 与 GitHub

- `docker/Dockerfile` 使用 Node.js 与 Python 多阶段构建：第一阶段通过锁文件构建 `web-app/dist`，最终镜像只包含 Web 服务、`core/`、静态前端、美术资源和 `requirements-runtime.txt` 中的运行依赖；Linux 部署包也复制同一个运行依赖锁文件。Dockerfile 使用官方源作为跨平台默认值，Compose 可通过公开构建参数为受限网络切换 ECR、npm 和 PyPI 镜像，不允许在构建参数中嵌入凭据。
- `docker/docker-compose.yml` 默认将 `127.0.0.1:8787` 映射到容器服务，并使用命名卷 `fyt-data` 持久化 `/data`；账号库、上传、输出、回收站和备份不进入镜像，执行 `docker compose -f docker/docker-compose.yml down` 或重建容器不会删除业务卷。局域网访问必须由管理员显式把 `FYT_WEB_BIND` 改为 `0.0.0.0`。
- 容器使用 UID/GID `10001` 的非 root 用户运行，根文件系统只读，删除全部 Linux capabilities，启用 `no-new-privileges`、PID 上限、30 秒优雅停止、临时目录限制和 `/api/health` 健康检查；Docker `json-file` 日志单文件最多 10 MB、保留 3 份。HTTPS、证书和 Cloudflare Tunnel 仍由宿主机代理或独立容器管理，不写入应用镜像。
- GitHub 源码仓库为 `KuroNeko-night/fyt-data-mgmt`。`scripts/sync-github.ps1` 与 `scripts/sync-github.sh` 默认只生成本地提交，显式指定推送参数后才访问远程；提交前拒绝运行数据、数据库、日志、证书、私钥、压缩包、依赖和构建产物。
- 仓库根 `AGENTS.md` 保存当前维护约束，GitHub 克隆和纯净源码包都直接包含该文件，不依赖本机仓库外层目录。
- `.github/workflows/ci.yml` 在主分支推送和 Pull Request 上执行 Python 3.11/3.13 回归、Web 构建和 Docker 镜像构建检查，只授予仓库内容读取权限，不自动发布镜像或部署生产环境。

### Linux 一键部署

- `packaging/linux/deploy-from-git.sh` 提供公开仓库直接部署入口：在 `/opt/fyt` 的受控临时目录克隆指定分支或标签，支持期望提交哈希校验；目标机缺少兼容 Node 时从可配置发行目录下载 Node 22 并验证官方 SHA-256，随后按锁文件构建 `web-app/dist`，组装与 Linux ZIP 相同的白名单载荷并调用 `install.sh`。克隆目录和 `node_modules` 在退出时清理，Node 工具和 npm 缓存单独保存在 `/opt/fyt/git-tools`，不进入正式服务目录。
- `install.sh` 依次选择 Python 3.13、3.12、3.11 或 3.10，在 Alibaba Cloud Linux 3 上可并行安装新版 Python，不替换系统 Python。
- 程序安装到 `/opt/fyt/server`，配置写入 `/etc/fyt-web/fyt-web.env`，业务数据写入 `/var/lib/fyt-web`，备份写入 `/var/backups/fyt-web`。
- systemd 使用低权限 `fyt-web` 账号、独立虚拟环境、UTF-8 环境和固定 HOME，只授予数据目录所需写权限。
- 公网入口采用 Cloudflare DNS 与 Caddy 反向代理：Cloudflare 添加 A 记录并启用代理，在 `SSL/TLS → Origin Server` 创建源站证书并设置 `Full (strict)`；Caddy 监听 443，并反向代理到 `127.0.0.1:8787`。`install.sh` 会调用 `caddy-setup.sh` 扫描 `/root` 顶层的 PEM 文件，只有识别到未过期且公钥匹配的证书/未加密私钥时，才从官方软件源（失败时使用 Caddy 官方下载接口）安装 Caddy、从证书 SAN 生成受控配置、注册 `caddy.service` 并执行本机 HTTPS 健康检查；未找到配套文件则保持现有 Caddy 配置不变并正常跳过。Cloudflare Named Tunnel 保留为无需开放 80/443 入站的备选方案。
- `start.sh`、`stop.sh`、`restart.sh`、`status.sh`、`logs.sh`、`backup.sh` 和 `update.sh` 提供统一运维入口；首次 Git 部署成功后，后续可直接运行安装目录中的 `deploy-from-git.sh` 拉取并部署新版本；`cloudflared.sh` 与 `cloudflared-named.sh` 管理临时或固定 Tunnel。

### Linux 增量升级补丁

- `scripts/build_linux_upgrade_patch.py` 只收集 `web_server.py`、`web_backend/`、`core/*.py`、`web-app/dist` 和运行依赖，生成 `fyt-linux-upgrade-patch-v<版本>-<日期>.tar.gz`、文件清单和 SHA-256。它与完整 Linux 包都只部署 `requirements-runtime.txt` 锁定的运行依赖，包内统一命名为 `requirements.txt`，不得把 PyInstaller 等开发依赖安装到服务器。
- `packaging/linux/apply-upgrade-patch.sh` 只替换程序文件，不读取、不复制、不删除 `/var/lib/fyt-web`。
- 应用补丁前备份当前程序；依赖变化时复用现有虚拟环境更新依赖；随后执行源码检查、启动服务和本机健康检查。失败时恢复程序文件与升级前服务状态。
- 完整安装包和增量补丁都把 `web_backend/` 纳入必要文件校验、暂存、权限设置与 Python 编译检查；增量升级同时备份并恢复旧版已有的后端模块，不读取或覆盖 `web-data`。

### 冻结与部署路径约定

- `web_server.py` 和 `web_control_gui.py` 在冻结环境中从部署包根目录定位 `web-app/dist`、`web-data` 和子程序。
- `_bridge_command()` 在冻结环境优先定位同目录或 `桥接/` 子目录的 `bridge_worker.exe`；源码环境使用 `python -m core.tauri_bridge`。
- Web 启动桥接子进程时显式设置 `PYTHONPATH`，工作目录使用账号运行目录或系统临时目录，不依赖部署目录名称或字符集。

## 九、维护约束

- `core/` 不导入 UI、不弹窗；错误向上抛，由前端转换为客户可理解的提示。
- 新业务先实现 `core/<feature>_core.py` 和合成数据测试，再接入桥接白名单、Web 动作、双端页面、主数据、结果投影和人工确认。
- 输出统一使用 `paths.resolve_output_dir()`；新功能注册 `FEATURE_DIRS`。
- Web 权限必须同时落实到前端入口和服务端接口；隐藏菜单不能替代鉴权。
- Web 输出、上传、缓存、运行目录和任务必须按用户 ID 隔离。
- 注释优先说明业务规则、状态失效、事务顺序、路径边界和兼容原因；简单语句不堆叠复述性注释，行为变化时同步修正相邻注释和本文。
- 修改行为、签名、权限、部署或模块后同步本文；本文只保存当前实现与现行维护约束。
- 发布到 GitHub 时排除 `.venv`、`node_modules`、`dist`、`target`、`web-data`、可执行 sidecar、生成 schema、日志、缓存、备份和真实业务数据。
