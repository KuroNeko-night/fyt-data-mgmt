# 前端视觉统一阶段 0：基线与展示口径

> 核对日期：2026-08-03  
> 适用范围：`web-app/`、`tauri-app/`、工作台看板相关的 `web_server.py` 接口  
> 本文只记录阶段 0 核对后的当前事实和展示决策，不记录未实现的后续方案。

## 一、阶段范围

本阶段完成现状核对、工作台指标口径确认和双端视觉基线采集。没有修改 `core/`、服务端权限边界、上传/预检/复核/执行/取消/下载协议，也没有提前建立阶段 1 的设计令牌或基础组件。

实际工作台入口已经确认：

- Web 由 `web-app/src/App.tsx` 组合 `DispatchBoard`，实际页面实现位于 `web-app/src/DispatchBoard.tsx` 和 `web-app/src/dispatch.css`。
- `web-app/src/DashboardPage.tsx` 没有被 `App.tsx` 引用；其中的 `Metric`、`OverviewPage` 也是旧工作台遗留，不能作为本轮工作台基线。
- Tauri 由 `tauri-app/src/App.tsx` 组合 `LocalWorkbench`、`ModePicker` 和 `RemoteWorkbench`，导航事实来源为 `tauri-app/src/data/navigation.ts`。
- Web 工作台数据来自同源 `/api/overview`、`/api/dashboard`、`/api/notifications`；Tauri 本地端通过 bridge 获取数据，浏览器预览模式使用 `tauri-app/src/lib/bridge.ts` 中的预览数据。

## 二、当前实现基线

### Web

- 外壳仍由 `App.tsx` 内联维护：侧栏、顶栏、会话、主题、移动导航和页面组合尚未拆成独立壳层组件。
- 当前 Web 视觉仍是蓝青品牌渐变、浅色玻璃表面、较大圆角和阴影；`DispatchBoard` 使用独立的 `.dsp` 局部令牌和深色状态带。
- 工作台桌面结构为深色状态带、任务流水、右侧趋势和待办；移动端仍使用底部横向导航。
- 首次进入已登录工作台会自动打开四步 `GuidedTour`；Web 引导目标仍使用侧栏按钮的 `nth-child` 选择器。
- 工作台无任务时，`快速开始` 当前因 `feature_usage` 为空而不渲染，任务流水仍提示从右侧快速开始，存在空态文案与实际布局不一致。

### Tauri

- 本地工作台保持 `224px` 侧栏、收起后 `64px` 侧栏和 `300px` 快捷面板；顶栏当前约 `92px`，内容最大宽度约 `1100px`。
- 首页同时展示品牌、归档数量、快捷入口和右侧最近任务；它与侧栏和快捷面板存在信息重复。
- `tauri-app/src/styles.css` 前半段是基础样式，后半段仍存在“流光工作台”环境光、视图过渡和重复选择器。
- 对账单扫描区域仍引用 Web 风格的 `--paper`、`--muted`、`--ink`，这些变量不在 Tauri 根令牌中定义。
- 标准 Tauri 视觉回归脚本已补充 `fyt-desktop-mode=local` 初始化，避免测试停留在模式选择页；该修正只影响测试启动状态，不改变应用运行时行为。

## 三、工作台指标契约

以下口径以 `web_server.py` 的 `dashboard()` 和 `/api/overview` 实现为准。除特别说明外，任务、结果文件和消息均按当前登录用户隔离。

| 页面展示 | 当前字段/来源 | 统计范围与时间口径 | 空值规则与备注 |
|---|---|---|---|
| 更新于 | `dashboard.generated_at` | 服务端生成看板响应的 UTC 时间，前端按浏览器本地时间显示 | 始终显示响应时间；当前界面带绿色“实时”圆点，但没有自动刷新协议，后续应改为普通更新时间表达 |
| 排队 | `status_breakdown.queued` | 当前用户全部 `web_jobs` 中 `status = queued` | 无记录显示 `0`；这是当前状态，不是历史累计 |
| 处理中 | `status_breakdown.running` | 当前用户全部 `web_jobs` 中 `status = running` | 无记录显示 `0`；这是当前状态，不是历史累计 |
| 待复核 | `status_breakdown.review` | 最近读取的最多 500 条当前用户任务中，复核动作且数据库状态为 `completed` 的任务被视为待确认 | 无记录显示 `0`；这是“需要用户确认”的状态，不应混入已完成 |
| 已完成 | `status_breakdown.completed` | 数据库完成数扣除待复核数后的结果；原始状态查询覆盖全部任务，但待复核修正使用最多 500 条任务 | 无记录显示 `0`；当前实现存在超过 500 条任务时的范围不完全一致风险 |
| 异常任务 | 前端 `failed + interrupted` | 当前用户任务的失败和中断数量 | 无记录显示 `0`；当前界面仍写“脱轨”，取消任务没有纳入该格 |
| 今日创建 | `trend` 最后一项的 `total` | 按业务日期统计今天创建的任务；业务日期由服务端固定 UTC+8 换算 | 无任务显示 `0`；不是按完成日期统计 |
| 今日创建中已完成 | `trend` 最后一项的 `completed` | 今天创建、当前状态已完成且不是待复核的任务数 | 无任务显示 `0`；不能称为“今天完成总量” |
| 近七日任务量 | `trend[].total` | 从业务今天往前含今天共 7 个自然日，按 `created_at` 的业务日期分桶；读取上限为最近 500 条任务 | 每天无任务仍返回并显示一根空柱；当前标题“近七日吞吐”不准确 |
| 近七日已完成 | `trend[].completed` | 同一创建日期桶内，当前状态已完成且不是待复核的任务数 | 当前趋势图没有直接展示该字段 |
| 近七日失败 | `trend[].failed` | 同一创建日期桶内，当前状态为 `failed` 的任务数 | 中断、取消没有计入失败段；图表只把失败段作为堆叠信息 |
| 功能使用排行/快速开始 | `feature_usage` | 最近读取的最多 500 条当前用户任务，按动作映射到业务功能后计数，取前 6 项 | 空数组时当前组件直接不渲染；后续工作台必须提供默认推荐入口 |
| 最近任务 | `recent_jobs` | 当前用户按创建时间倒序的前 8 条任务 | 无记录显示任务空态；包含排队、处理中、待复核、完成、失败等状态 |
| 最近输出 | `recent_files` | 从当前用户按创建时间倒序扫描的已完成任务中取文件，最多 6 个；单个任务最多取 5 个文件 | 文件通过 `job_id` 关联到任务流水；文件可能来自前 8 条任务之外的较旧完成任务，前端当前只在对应任务存在时显示 |
| 工作台待办 | `dashboard.notifications`、复核数、管理员待审核数 | 通知为当前用户有效公告和定向消息，混合查询最多 12 条；复核数按当前用户；待审核账号数为全局数且仅管理员显示 | 已读通知也会进入“需要处理”；当前通知并不等于未读数 |
| 侧栏未读数 | `/api/notifications.unread_count` | 当前用户有效公告最多 20 条、定向消息最多 20 条，合并排序后最多保留 30 条，再统计未读 | `App.tsx` 单独请求该接口；工作台响应中也有 `unread_count`，但当前未使用，存在重复契约 |
| `/api/overview` 旧指标 | `pending_users`、`approved_users`、`output_jobs` | 待审核账号和已审核账号为全局数；`output_jobs` 为当前用户数据库状态为 `completed` 的任务数 | `OverviewPage` 未被渲染，`output_jobs` 当前只保留在接口契约中 |

### 展示决策

阶段 0 确认后续工作台应采用以下客户化语义：

1. 将“排队、处理中、待复核”作为当前任务状态块，取消把“已完成”放在同一条误导性流水线上。
2. 将“脱轨”改为“异常任务”或“失败或中断”，不把失败描述为业务阶段。
3. 将“近七日吞吐”改为“近七日任务创建量”，补充“按任务创建日期统计”。
4. 将“今日已完成”改为“今日创建 / 其中已完成”，直到服务端提供完成时间并完成统一聚合前，不宣称按完成日期统计。
5. 通知、未读数、待复核和管理员待审核继续保持各自数据来源，不在前端合并计算；后续统一视觉组件时只统一状态语言，不改变权限和数据隔离。
